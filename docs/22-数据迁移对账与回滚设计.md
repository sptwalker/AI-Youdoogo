# 22-数据迁移对账与回滚设计

> 关联：docs/21-通用AI平台拆分架构与落地方案（D 组「测试与迁移准备」的 D6 交付）。
> 配套代码：`scripts/reconcile.py`（指纹）、`scripts/inventory_assets.py`（D5 计数基线）、
> `scripts/llm_replay.py`（D4 离线 parity）、`scripts/retrieval_golden.*`（D3 检索 parity）。

## 1. 目标与边界

通用 AI 平台拆分（docs/21）把 LLM 完成、知识索引、专家等能力从本进程迁到远端服务。迁移期采用
**Branch-by-Abstraction**：同一端口（如 `LlmCompletionPort`）本地/远程两实现并存，靠开关切换。本文只
解决迁移期两个可验证问题：

1. **对账**——切流前证明「远程结果 == 本地结果」（内容一致，非字节一致）。
2. **回滚**——切流后若远程劣化，如何安全切回本地且不丢数据、不重复投递。

**边界**：AI 红线不变（AI 仅建议/分析/辅助执行，业务/资金/项目/人事决议需真人确认）；对账/回滚是**运维动作**，
不改业务语义。**不新建对账存储**——复用现有表 + 只读脚本（YAGNI）。

## 2. 对账字段与指纹

### 2.1 content_hash（数据完整性锚点）

对账不比字节，比**业务内容**。`scripts/reconcile.py::content_hash(fields)` 把一行的业务字段折成确定性
sha256 指纹：

- **键序无关**（`sort_keys`）——dict 插入序不改变指纹；
- **跨进程稳定**（`ensure_ascii=False` + 紧凑分隔符 + `default=str` 折叠 uuid/datetime/Decimal）；
- **None 与缺列可区分**——漏列不会被误判为一致。

确定性由 `tests/test_reconcile.py` 钉住（键序/值敏感/None-vs-缺列/复杂类型）。

### 2.2 参与与排除的字段

| 类别 | 是否入 hash | 说明 |
|---|---|---|
| 业务内容（prompt_template、message content、专家定义、model_role、usage 语义…） | ✅ 入 | 迁移必须保真的部分 |
| 技术簿记（`id`、`created_at`/`updated_at`、租约列、`migration_batch`、`source_ref`） | ❌ 排除 | 由调用方选列时剔除；两端天然不同，入 hash 必假阳性 |

**排除由调用方负责**：`reconcile.py` 只做「业务字段 → 指纹」纯函数，选哪些列是对账脚本按表决定的口径。

### 2.3 迁移簿记列（写在目标侧，不入 hash）

远程侧每行带三列可选簿记，供审计与回滚，不参与 content_hash：

- `source_ref`——源库主键（UUID），双跑期定位「这行从哪来」；
- `content_hash`——写入时算好的指纹，对账时直接比，免重算源侧；
- `migrated_at` / `migration_batch`——迁移时间与批次，回滚时按批次圈定影响面。

> 这三列是**迁移期临时列**，切流稳定、兼容层删除后一并 drop（见 §4 最后一步）。

## 3. 对账流程

分三关，全部离线可跑（不依赖真实远端）：

1. **计数基线（D5）**——`scripts/inventory_assets.py` 出各资产类计数 + 归属 + 跨界依赖。迁移前后各跑一次，
   **计数必须相等**（行数守恒）。这是最粗但最先失败的关，先过它再谈内容。
2. **内容 parity（D3/D4）**——逐行 `content_hash` 比对源↔目标：
   - LLM 完成：`scripts/llm_replay.py` 用录制样本离线回放，证明远程适配器产出与录制一致；
   - 检索：`scripts/retrieval_golden.*` 金标样本比 top-k 排序；
   - 失配即列出 `source_ref` + 两侧 hash，人工核因，**不自动改数据**。
3. **抽样人工核对**——parity 全绿后，抽 N 行真人肉眼比内容（防「指纹口径本身选错列」这类系统性偏差）。

三关全绿 = 具备切流条件。任一关红 = 停在本地，修好再来。

## 4. 回滚设计

回滚不是「删远程数据」，而是**把权威源切回本地**。按 Branch-by-Abstraction 分步，每步可独立停留：

1. **开关回切**——端口实现开关从 Remote 翻回 Local（配置层，`app/core/runtime_config.py` 覆盖）。新请求即刻走本地，
   **无需改代码、无需发版**。这是回滚的第一动作，秒级生效。
2. **源权威并行窗**——回切后，本地库仍是权威（迁移期本地从未停写，只是被开关旁路）。远程侧写入作废，不倒灌回本地
   （避免远程劣化数据污染权威源）。
3. **在途 workflow 排空**——已进 durable runtime（`WorkflowRun/WorkflowStep`）的多步任务按幂等语义自然跑完或
   defer；outbox 未投递事件由现有租约 worker 续投，**不丢事件**（依赖 outbox 事务外发箱的既有幂等/dedupe）。
4. **兼容层最后删**——远程稳定运行、对账连续 N 天全绿后，才删本地兼容实现与 §2.3 迁移簿记列。**删除永远是最后一步**，
   在此之前本地路径必须可秒级切回。

### 回滚触发条件（运维口径，非本文强制阈值）

- 对账 parity 失配率超阈值；
- 远程 P99 延迟/错误率超 SLO；
- 远程不可用且重试耗尽（outbox 事件落 `OUTBOX_FAILED` 死信区堆积）。

阈值与告警归监控栈（Prometheus 规则），不在 app 内建告警器。

## 5. 不做什么（YAGNI）

- **不建对账表/对账服务**——只读脚本 + 现有表足够；对账是迁移期一次性动作，不是常驻能力。
- **不做自动数据修复**——失配一律人工核因，防脚本把「口径 bug」当「数据 bug」批量改错。
- **不做双向同步**——回滚单向（远→本地作废），本地始终权威直到兼容层删除。
