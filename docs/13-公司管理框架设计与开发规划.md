# 13-公司管理框架设计与下一阶段开发规划

> 基准底座：v0.3.0（迁移链 001~009）。本阶段只搭"管理框架"，不做具体业务流程；未来再挑 1~2 个重点业务打通人机协作工作流。
> 红线不变：AI 仅有建议/分析/辅助执行权，一切"生效动作"必须真人确认，全程留痕可溯源。
> 本文由多视角设计工作流（7 视角 → 综合 → 批判）产出并已并入批判修正，**标注「待确认」的条目见第 8 章**。

## 0. 三条横切契约（keystone — 先定这三条，其余全部塌缩为重复应用）

> **人机定位（2026-07-13 确认）**：AI 智能体一律定位为**顾问/助理**（协助并代理真人），真人担任正式职位、持最终决定权。命名约定：`tier=exec`→公司**顾问**（首席X顾问，如 CPO=首席产品顾问、CCO=首席创意顾问）；`tier=director`→**总监助理**；`tier=member`→**助理**。**CEO=最高管理员（真人），无 CEO Agent**；公司顾问直属真人 CEO（`report_to=NULL`）。种子含 8 顾问（CPO/CCO/COO/CTO/CMO/CBO/CHO/CFO）+ 9 总监助理（含公共设计组，CCO 代理）。智能体按 code 稳定寻址（`ops` 已改 code 查找），显示名可随时改不影响功能。

**契约①：统一归属 = 一个 `department_id`（组织节点）。** 把"公司"本身建成组织树的**根节点**（`node_type=company, level=0, parent_id=NULL`）。于是"公司级/一级/二级"统一为一棵树上的节点，一切资源归属统一表达为"指向某 `department_id`"，company 级资源 = 指向根节点。仅知识库因有"个人知识区"（归属 agent）额外保留 `scope` 枚举。

**契约②：默认可见性规则（默认全公司可见 + 机密标记 · 减法隔离）。** 【已确认：采纳"默认可见+机密标记"】
资源两态：**public（默认）/ confidential**。
- **public 资源**（company/department scope 且未标机密）：**全员可见**（贴合高信任重协作团队；也与现状"检索全局开放"一致，回归风险最低）。
- **confidential 资源**（显式标机密）+ **personal 资源**（高管/总监专属知识区，天然私有）：仅"归属方 + 显式授权 `resource_grant` + admin"可见。
  - confidential 资源归属节点 X → 可见于 X 子树成员（`principal.path` 落在 `X.path` 内的真人+AI）+ 授权 + admin；
  - personal 资源 → owner agent 本人 + 授权 + admin。
- **隔离是减法**：默认放开，把敏感资源（财务/HR/薪酬等）逐个标 confidential 收紧，而非默认全关再逐个开。
- admin 全部可见（决策⑥：可见但每次跨部门检索落 `audit_log`）。

**契约③：幂等 + 审计。** 模板初始化按稳定自然键 `code` 做 upsert（可重入）；所有真人"生效动作"和配置/组织/权限变更强制写 `audit_log`。**软删（`is_delete`）× 唯一约束的互斥必须先系统性修复**（改为 `WHERE is_delete=false` 的部分唯一索引），否则"删了重建同名"必撞库。

### 1.2 扩展表 · 字段级

**`sys_department`（树化）**：`+parent_id`(FK self,null,根为NULL)、`+node_type`(company/dept_l1/dept_l2)、`+level`(SmallInt 0/1/2，禁 >2)、`+path`(物化路径 `/{root}/{l1}/{l2}/`，子树 `path LIKE '/{id}/%'`)、`+sort_order`、`+supervisor_user_id`(FK sys_user,null；**每个部门节点对应一名真人主管**，根节点=公司级主管/admin；跨部门协作的确认/复核由此人执行)。唯一约束：`name` 全局唯一 → `unique(parent_id, name)`；`code` → 部分唯一 `WHERE is_delete=false`。**人机配对**：每部门 = AI 总监（`agent_role tier=director`，领活/执行）+ 真人主管（`supervisor_user_id`，确认/监督），前者派生不入表、后者显式一列。

**`agent_role`（升格为 AI 员工）**：`+code`(String64，**稳定种子键**如 `exec_cpo`/`dir_platform_ops`，部分唯一)、`+tier`(exec/director/member)、`+title`(可编辑显示名)、`+report_to_id`(FK self，汇报线)、`+is_seed`(保护骨架)。`name` 改部分唯一。**`tier`(组织层级) 与 `model_role`(LLM 档位 daily/reasoning) 正交**：普通员工默认 `model_role=daily`（成本红线），种子里二者分别显式设。现有 `permission_scope` JSONB **降级为工具/额外授权提示**，访问控制统一走 scope 推导 + `resource_grant`。

**`knowledge_file`**：`+knowledge_base_id`(FK，先 nullable 回填后置非空)。
**`meeting_info`**：`+department_id`(FK null)。`participants` JSONB 不动。
**`task_card`**：`+department_id`、`+assignee_type`(agent/user default agent)、`+assignee_user_id`(派真人)、`+origin_type`(proposal/meeting/manual)。**状态机不改**。调度器 `run_task` 需按 `assignee_type` 跳过"派真人"任务（现遇 assignee_agent_id 空即抛错）。
**`ops_daily_metric`**：`+department_id`——**注意 upsert 幂等键需重定义**（原 `(stat_date,product)` → 含 department_id）。**`llm_call_log`**：`+department_id`（日预算告警从全局升级到部门归集）。

### 1.3 新建表 · 字段级（均含 CommonMixin）

- **`knowledge_base`**：name｜code(unique)｜scope(company/department/personal)｜department_id(FK null)｜owner_agent_id(FK,personal 必填=高管/总监专属知识区)｜**is_confidential**(Bool default false，标机密→收紧为归属方+授权可见)｜description｜is_default｜is_active。全库**单一 1024 维 embedding**（跨可见库并集检索前提），换模型=全局重建。
- **`data_source`**：name｜code(unique)｜type(thinkingdata/feishu_bitable/feishu_docx/excel/http_api)｜department_id(FK，公司级=根)｜config JSONB(**仅非密参数**)｜secret_ref(指向 .env 变量名，**绝不存明文密钥**)｜is_active。现有 feishu/thinkingdata/excel client 零改动，本表只做"可发现+范围+配置"元数据层。
- **`discussion_channel`**：name｜department_id(挂节点)｜default_agent_id(空@缺省目标)｜creator_id｜is_archived。部门创建时种子自动建 1 频道。
- **`discussion_message`**：channel_id｜speaker_type(human/ai)｜speaker_id(松引用)｜speaker_name(冗余留痕)｜content｜mentioned_agent_ids JSONB(@目标)｜ai_source_record_id(AI 发言关联 agent_task_record)｜ref_type/ref_id(升格产出 proposal/meeting/task 溯源)。
- **`resource_grant`**（唯一权限表，只存例外/跨节点/私有覆盖）：resource_type｜resource_id｜grantee_type(**user/agent/department**，砍 role)｜grantee_id｜perm(read/write/admin)｜granted_by(审计)｜expires_at。**grant 到某节点 = 覆盖其子树，读时判定**。**红线固化**：grant 只授"内容访问权"，绝不授"生效权"。
- **`audit_log`**（追加式）：actor_id(null=系统)｜actor_role(角色快照)｜action(config.update/task.accept/…)｜target_type/target_id｜summary｜detail JSONB(**密钥字段落库前打码**)｜ip｜result。索引 create_time/actor_id/action/(target_type,target_id)。
- **`sys_config`**（非密可编辑）：key(unique)｜value JSONB｜value_type(驱动前端渲染+校验)｜category(llm/feishu/embedding/dataif/feature/log)｜is_editable｜updated_by。经 `config_service.resolve(key)` 两层解析：`sys_config`(DB) → `Settings`(.env 兜底)。改后即时生效。

### 1.4 身份寻址（不建合并表）
`Principal = (principal_type ∈ {user, agent}, principal_id)`；真人=sys_user、AI 员工=agent_role，二者都挂 department_id。可选只读视图 `v_org_member = sys_user ∪ agent_role` 供花名册单一 join。

## 2. 三层执行体系 + MVP 重锚定

| 层 | 承载实体（现有） | 驱动器（现有） |
|---|---|---|
| **业务执行层** | `agent_role`(升格为员工) → `agent_task_record` | `run_agent` |
| **任务分配层** | `task_card` + `task_card_log` | `scheduler.run_task` + `task_flow` |
| **决策互动层** | `proposal_*` / `meeting_*` / `discussion_*` | `proposal_service`/`meeting_service`/新 `discussion_service` |

**层间只经"真人闸门"通信**（已有字段）：决策层 →(真人确认)→ 分配层（`converted_task_id`）；分配层 →(dispatch)→ 执行层（scheduler 拾取）；执行层 →(reported)→ 分配层（回填 result）；分配层 →(真人 accepted)→ 生效。执行层/分配层遇阻只能"产出提案/挂议题"回真人评审，AI 不能自改决策层。**桌面是执行层本地视图：只读自己的任务、只写回 result，绝不直接触碰决策层表**——这是三层解耦的物理边界。

**MVP 重锚定（全部加列，零重写、零状态机改动）**：任务卡加 department_id → 按部门过滤任务流；提案已有 department_id；会议加 department_id，`ai_expert_speak` 是讨论区 @触发的现成范本；知识库入库携 kb_id、检索按身份 scope 过滤；运营数据按部门切片。

**真人工作桌面（2026-07-13 确认，取代原「AI 员工桌面」设计）**：桌面是**真人员工的统一工作枢纽**，不是 AI 员工的（AI 员工无桌面、不登录）。聚合接口 `GET /desktop/{user_id}`（本人；admin 可查他人做监督），零新表：**待我处理**（统一队列：待验收任务+待评审提案+待确认决议+待复核协作请求，类型标签区分，同性质不拆分）＋**我的任务/发起**（我创建/负责的任务 + 一键发起任务/提案/协作请求交 AI 顾问或人机混合流程）＋**对话入口**（进协作空间频道 @AI 顾问，复用现有协作空间）＋**资料入口**（我 scope 内知识库）。每人只见自己，admin 全见。**它就是现有「真人工作台」(Dashboard) 的完全体，同一页面，不另建。**

### 2.1 检索范围隔离 + principal 穿透（P0 · 唯一有回归风险的双扇出，F2 一次做净）
1. 新增纯函数 `resolve_visible_kb(db, department_id, owner_agent_id, is_admin, extra_kb_ids)` → 按契约② 算可见库 id 集：**默认 = 所有 active 且非机密的 company/department 库**（全员可见）∪ 归属本节点子树的机密库 ∪ 本人 personal 库 ∪ `resource_grant` 授权库；admin=全部（跨部门检索落审计）。
2. `retrieval.search()` 增参 `visible_kb_ids`，在既有 `JOIN knowledge_file` 加 `WHERE knowledge_base_id IN (...)`；空集直接返回"资料不足"。
3. **扇出一**：所有 retrieval 调用方（knowledge api / meeting 预研 / proposal 预研）一次性传入可见集。
4. **扇出二（同量级，易漏）**：`run_agent` 及其调用方（`ai_expert_speak`/proposal 预研/scheduler）现只传 `user_id`，需一并穿透 `(principal_type, principal_id, department_id)`，否则 AI 员工检索拿不到自己的 scope。
> `# ponytail: 现精确全扫+JOIN 过滤够用；单可见语料 >数万 chunk 或延迟超标时，把 knowledge_base_id 反范式到 knowledge_vector 做 ANN 预过滤`

### 2.2 人机协作与委派治理（跨部门）【已确认 2026-07-13】

**三种"调用"模式**：A 真人→本部门 AI（直接委派，绿灯）；B AI→跨部门**数据/知识资源**（只读，按契约② 可见性门控：公开默认可读、机密需授权，透明完成）；C AI→**其他部门 AI 员工**（跨部门人力调配，走下述治理）。

**C 的治理 = 分发闸门做风险分级 + 生效闸门永远真人**：

| 跨部门协作 | 低风险（分析/草拟/取数/预研，不直接生效） | 高风险（触及红线：资金/人事/项目/重大业务调整） |
|---|---|---|
| 无既定工作流授权 | 调度中枢**自动分发** + 事后真人主管复核 | **单项 pre-确认**后再分发 |
| 有既定工作流授权 | 自动分发 + 事后复核 | 自动分发 + 事后复核（工作流已预审） |

- **红线不可动摇**：风险分级只放松"分发闸门（谁准许开始干活）"；**产出的"生效"（草稿→正式决议/执行）永远真人确认**——即便自动分发，AI 产出仍是草稿，须真人验收才作数。
- **确认人 = 目标部门真人主管**（`sys_department.supervisor_user_id`）：被消耗资源/人力的部门主管确认或复核；公司级（根节点）协作由公司级主管/admin。
- **两种确认粒度**：**单项业务确认**（针对一次请求）/ **既定业务工作流确认**（目标主管预授权一条"源部门→本部门、某类协作"的通道，实例自动跑 + 事后复核）。
- **风险默认分类**：红线类别（资金/预算、人事、项目立项/调整、重大业务调整）= **恒高风险**；分析/草拟/取数/报告/预研等只产草稿的 = **默认低风险**；发起方或主管可手动升级某请求为高风险。
- **同部门内** AI 之间沿 `report_to_id` 拆解流转（总监 AI → 本部门员工 AI）属执行权范畴，调度中枢自动流转、产出仍真人验收，不设跨部门闸门。
- 依据既有铁律 docs/04 §5「跨部门任务由调度中枢统一拆解分发，禁止 Agent 私自跨部门指派」——AI 永远只"产出协作请求"，分发与确认由调度中枢 + 真人主管执行。

**框架 vs 工作流的分工**：本阶段（框架）只落**结构**——`supervisor_user_id`（F1）、`task_card` 加 `risk_level` 与跨部门归属、`collab_authorization`（既定工作流授权）容器 + 主管复核队列/UI（F4/F5）；**自动编排链**（AI 产出请求 → 匹配授权/风险 → 自动分发或转确认 → 执行回流 → 事后复核）在"打通 1~2 个重点业务工作流"的**未来阶段**才接起来跑。

## 3. 管理员配置系统 + 前端信息架构

| 能力块 | 管理员做什么 | 落点 |
|---|---|---|
| **组织搭建** | 一键初始化骨架；建两级部门树；员工分配部门/层级/汇报线 | `org_template` 幂等种子 + sys_department + agent_role |
| **部门资源配置** | 选中部门 → 绑定 智能体/知识库/会议室/讨论区/数据接口 | 各资源表写 department_id |
| **系统级配置** | AI API / 飞书 / 数据接口 / 用户权限 / 系统日志 | sys_config + data_source + resource_grant + audit_log + 复用 llm_call_log/agent_task_record |

**配置存储策略（2026-07-14 调整：密钥可 UI 填写）**：密钥（各 *_api_key/飞书 secret/TD secret 等）**可存 `.env` 或 `sys_config`（系统配置页 UI 填写，`is_secret=true`）**；app 经 `runtime_config` 覆盖层读取（sys_config 覆盖 .env，未填回退 .env，平滑迁移）；list 接口对密钥**脱敏**（只回 `is_set` 状态，不回显明文）、审计 detail 打码、绝不硬编码。系统配置页按分类分栏（AI/向量/外部数据/飞书/提示词/功能）+ 连通性测试。JWT 密钥仍留 .env（启动即校验）。

**前端信息架构（2026-07-13 确认：菜单二级分组）**：
- **业务**（全员按权限）：真人工作桌面（=工作台完全体）｜知识库｜运营看板｜智能体｜任务卡｜提案｜会议｜协作空间。
- **系统管理**（仅 admin）：组织架构（部门树 + 初始化 + 员工分配）｜用户与权限（用户 CRUD + 角色 + 部门 + **resource_grant 授权**）｜系统配置（字段由 value_type 动态渲染；AI API/飞书页只做**脱敏状态位 + 连通性测试**，不改密钥）｜数据接口（data_source CRUD + 连通性测试）｜知识库集合（knowledge_base CRUD + 机密标记）｜智能体架构（部门×三级 + 汇报线）｜系统日志（操作审计/AI 调用/智能体执行）。
- **不做**：「部门资源配置」独立页取消——改为各资源列表加「改部门」；无「会议室」tab（会议挂 department_id，不建 meeting_room）。

**幂等种子** `app/services/org_template.py::seed_org_template()`（不进 Alembic，是业务配置、需可重入可测）：按 `code` upsert 公司根 + 8 个一级部门（基础产品/游戏研发/平台运营/商务合作/营销销售/品牌宣传/人资行政/财务）+ **7 高管 Agent（CPO/CTO/COO/CMO/CBO/CHO/CFO，挂根，reasoning，is_seed）** + 8 总监 Agent（挂各 L1，daily，is_seed，report_to 对口高管）；管理员 `POST /api/v1/org/init-template` 触发；现有 2 种子（运营AI总监→dir_platform_ops 复用为平台运营部总监/会商AI专家→agent_meeting_expert 公司级共享推理体）在迁移里映射并入并标 is_seed。**不设 CEO Agent——CEO=最高管理员(真人 admin)，即公司根节点的真人主管、系统最高权限者**。配 `sys_config('org_template_version')` 防重灌。

**审计落点**（不做全局中间件，在既有生效动作函数内显式 `audit()`，恰好覆盖红线全部真人确认点，约 10 处）：任务验收｜提案通过｜会议决议确认｜提示词应用｜用户/权限变更｜配置变更｜组织/资源绑定/模板初始化。每点留一个 assert/最小 test 防漏。

## 4. 提示词分层治理（批判补充 · 最欠设计的一块）

几十个 agent 各存整段自由 `prompt_template`，会导致"改一次全局红线要编辑几十行"。改造：`run_agent` 在系统消息里**分层拼装** = 全局不变量前缀（红线免责/禁幻觉/可溯源/公司口吻，取自 `sys_config`）+ 部门上下文 + 该 agent 的 `prompt_template`（只存角色特有段）。一处改全局策略。**红线的服务端真正控制点**不是 `require_human()`（那是纵深防御），而是"**生效动作永远不进 agent tool 注册表**"这条代码/评审纪律——AI 员工经 `run_agent` 内部运行、不持 JWT，唯一可能触碰生效动作的路径是 tool 直调服务函数，故 tool 白名单永不含 approve/accept/confirm 类。

## 7. 关键风险与红线固化（批判提炼）

- **软删×唯一约束**：系统性 bug（sys_user.username / sys_role.code / proposal_card.code 等全中招），F1 定全局策略一次覆盖。
- **agent_role 无稳定种子键**：现仅 name（可编辑），必须加 code 否则重跑 init-template 造重复高管。
- **双扇出漏一半**：retrieval scope 之外，principal 穿透进 run_agent 是同量级改造，F2 合并做。
- **成本红线**：几十 member 若默认 reasoning 则 token 数倍——member 默认 daily。
- **@Agent 成本**：无护栏则每句闲聊烧 token——五件套护栏。
- **admin 全库检索**：默认可见但每次跨部门检索落 audit_log（监督 vs 机密的折中）。
- **密钥安全**：env 唯一入口 + 脱敏状态 + 连通性测试不回显密钥 + audit detail 打码。
- **scheduler 派真人**：run_task 遇非 agent 受理方要跳过而非抛错。

1. **8 部门 → 7 高管汇报映射（含 CFO）**【已确认】：基础产品→CPO；游戏研发→CTO；平台运营→COO；营销销售+品牌宣传→CMO；商务合作→CBO；人资行政→CHO；财务→CFO。
2. **agent_role 加稳定 `code` 作种子键**（name/title 可自由编辑）。默认：加。
3. **软删×唯一约束全局策略**：所有业务唯一键统一改部分唯一 `WHERE is_delete=false`。默认：是。
4. **员工与人机身份模型**【已确认】：agent_role=组织"员工"主体（AI），真人是管理/监督层（挂部门、用现有工作台、可监督 AI 桌面）。
