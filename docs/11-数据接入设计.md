# 11-数据接入设计（提纲版）

> 状态：提纲级文档，阶段2开发前细化为字段级设计。
> 上游依据：docs/01（3.1 信息收集与数据治理）、docs/02（数据存储层）、docs/03（业务时序数据表）、CLAUDE.md 技术栈。
> 已确认数据源（2026-07-11）：飞书 + 内外部业务数据平台 API + Excel/文档人工上传。

## 1. 总体原则

- 数据接入是全系统的"入水口"：所有 AI 分析、监控告警、报告生成均以此处入库的数据为唯一依据，杜绝无来源输出。
- 三类数据源统一落入现有存储：结构化/时序 → PostgreSQL（TimescaleDB 时序表，`timescale/timescaledb-ha:pg16` 单镜像）；非结构化文档 → MinIO + 向量化入 pgvector；缓存与任务状态 → Redis。
- 治理流程统一：接入 → 清洗 → 标准化 → 异常标记 → 去重 → 入库，每一步留痕可追溯。
- 代码位置：解析与清洗逻辑在 `app/services/`；飞书客户端在 `app/integrations/feishu/`；定时任务用 APScheduler（随 FastAPI 进程运行）。

## 2. 三类数据源接入方式

### 2.1 A 类：Excel/文档人工上传（阶段2首先实现）

- 场景：各部门（首个为平台运营部）例行报表、日常运营数据 Excel，以及周报/纪要/制度等文档。
- 流程提纲：
  1. 前端/接口上传 → 文件落 MinIO，元数据写 `knowledge_file`
  2. 解析：Excel 用 openpyxl/pandas 按模板解析；文档（docx/pdf/md）走知识库解析分块管道
  3. 标准化：字段映射到统一口径（见第3章），校验必填列、类型、日期格式
  4. 入库：结构化数据 → TimescaleDB 时序表；文本内容 → 分块向量化入 pgvector（`knowledge_vector`）
  5. 反馈：返回解析结果摘要（成功行数/失败行数/异常明细），失败可下载错误报告后修正重传
- 模板化表头约定（细化时定稿）：
  - 每类业务数据发布一份官方 Excel 模板：固定表头行、字段名、单位、日期格式（YYYY-MM-DD）、必填标记
  - 模板带版本号（如 `运营日数据模板_v1.xlsx`），解析器按表头指纹识别模板版本
  - 非模板文件拒收并提示下载模板，不做自由格式猜测

### 2.2 B 类：业务平台 API 拉取（阶段2内实现，晚于 A 类）

- 场景：公司内外部业务数据平台（销量、用户活跃、渠道等），接口清单需先盘点（见附录 A）。
- **运营数据平台已确认为 ThinkingData（数数科技 TE），接口调研纪要见附录 B。**
- 流程提纲：
  1. APScheduler 定时任务（每日/每小时，按数据源配置）→ httpx 异步拉取
  2. 拉取窗口：按 `last_sync_time` 增量拉取，支持手动补拉历史区间
  3. 清洗与标准化（第3章统一口径）→ 写入 TimescaleDB 时序表（hypertable）
  4. 同步日志：每次任务记录数据源、时间窗、条数、成败、耗时，失败告警重试
- 前置条件：完成附录 A 接口盘点、向平台方索要 API 文档与鉴权凭证（阶段0动作，见第5章）。

### 2.3 C 类：飞书抓取（阶段2后段/阶段3，依赖 docs/10 缺口补齐）

- 场景：飞书多维表格（bitable）中的业务台账、飞书云文档中的周报纪要。
- 流程提纲：
  1. 复用 `app/integrations/feishu/` 异步 httpx 客户端（自研，不用 lark-oapi SDK）
  2. bitable 读取：定时拉取指定 app_token/table_id 记录 → 字段映射标准化 → TimescaleDB 或业务表
  3. 文档读取：拉取文档纯文本 → 走知识库分块向量化管道
  4. 依赖：docs/10-飞书集成设计 中列出的能力缺口（bitable 读取、文档读取接口）补齐后方可开工；自建应用权限申请为阶段0动作
- 首版只读不写（抓取入库），飞书消息推送等写能力按 docs/10 规划另行排期。

## 3. 数据治理提纲

统一治理管道，三类数据源共用（细化时落为 `app/services/` 内可复用函数）：

- **清洗**：去空行/空值处理策略（置 NULL/默认值/整行拒收，按字段配置）、类型转换、编码统一 UTF-8、前后空白与全半角归一
- **标准化口径**：
  - 统一维度字典：部门名、产品名、渠道名映射到系统编码（维护映射表，未识别值进待处理队列）
  - 统一时间：全部落库为带时区 timestamp，业务日期口径（自然日/统计日）在字段级注明
  - 统一单位与币种：入库前折算为约定基准单位
- **异常值标记**：不删除只标记——超出合理区间（规则阈值，后期可加统计法）打 `is_abnormal` 标记并写异常原因，供智能体监控告警消费
- **去重**：
  - 结构化：按业务唯一键（数据源+指标+日期+维度）幂等 upsert，重复上传/重复拉取不产生重复行
  - 文档：文件内容 hash 去重，重复上传提示已存在

## 附录 B：ThinkingData Open API 调研纪要（2026-07-12）

> 官方文档：[Open API 总览](https://docs.thinkingdata.cn/ta-manual/latest/technical_document/open_api/open_api.html)、[数据自定义查询 API](https://docs.thinkingdata.cn/ta-manual/latest/technical_document/open_api/data_api.html)；用户提供入口：[docs-v2 open_api](https://docs-v2.thinkingdata.cn/?version=latest&lan=zh-CN&code=open_api&anchorId=)

### B.1 鉴权

- 密钥在 TA 服务端用 `ta-tool` 命令生成：
  - `ta-tool generate_root_secret` — root 密钥，全项目可用
  - `ta-tool generate_api_secret -appid <APPID>` — 项目级密钥（**推荐**，最小权限原则）
- **重复生成同一密钥会使旧密钥失效** —— 轮换密钥必须同步更新本系统 `.env`（`THINKINGDATA_API_SECRET`，阶段2加入 config）
- 传递方式：URL 参数 `?token=$API_SECRET`（注意：token 在 URL 上，同步日志/异常信息中须脱敏）

### B.2 访问格式与核心接口

- 请求格式：`http://$HOST:8992/$API_PATH?token=$API_SECRET`（私有化部署默认端口 8992；实际 HOST 待确认）
- 平台共 11 类接口（模型查询/自定义查询/用户分群标签/维度表/数据集/SQL生成/元数据/看板报表/用户管理/项目管理/指标查询）。本系统首期只用**数据自定义查询**：

| 接口 | 方式 | 适用 |
|---|---|---|
| `/querySql` | 同步 SQL 查询 | 小结果集（日汇总指标） |
| `/open/execute-sql` | 提交后按 taskId 分页取数 | **首选**：日增量明细拉取（页大小最小1000/默认10000行） |
| `/open/submit-sql` | 异步任务 + 状态轮询（进度0-100%） | 大区间历史补拉 |

- 主要参数：`token` / `sql` / `format`（json、csv、tsv、json_object）/ `timeoutSeconds`
- 响应：`{return_code, return_message, data}`，`0`=成功，**`-1005`=请求频率过快（限流）**

### B.3 接入设计要点（阶段2细化）

- **客户端已实现**：`app/integrations/thinkingdata/client.py`（2026-07-12）——封装 `/querySql`（同步小结果集）与 `/open/execute-sql` + `/open/sql-result-page`（分页逐行产出）；`-1005` 指数退避重试（最多3次）；token 不进日志与异常信息；`/open/submit-sql` 异步任务留待历史补拉需求出现时再加。配置项 `TD_BASE_URL` / `TD_API_SECRET`（`.env`）。respx 单测 6 条全过，真实联调待 B.4 落实。
- 定时任务按 `last_sync_time` 增量拉取（SQL 带日期条件），走分页接口；历史补拉走异步接口
- 限流处理：收到 `-1005` 指数退避重试；拉取任务串行化，不并发打接口
- 密钥经 `app/core/config.py` 环境变量读取，符合密钥管理铁律
