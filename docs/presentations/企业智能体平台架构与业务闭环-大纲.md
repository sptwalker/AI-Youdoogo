# 企业智能体平台架构与业务闭环——PPT 大纲

## 汇报定位

- 面向对象：管理层、业务负责人、产品负责人和技术负责人。
- 核心问题：企业智能体如何接收宽泛业务目标，形成受控执行，并把真实业务结果纳入可治理的改进闭环。
- 建议时长：25～35 分钟。

## 统一表达规则

整套 PPT 使用三类事实标签，避免把规划能力写成当前能力：

- **目标规范**：`20-DDD领域边界与分层架构规范.md` 定义的目标运行架构和领域边界。
- **当前实现**：当前源码已经存在并受代码约束的状态、动作和前置条件。
- **目标接续**：业务上希望形成、但当前代码尚未自动打通的后续链路。

## 页面结构

### 1. 封面：企业智能体平台架构与业务闭环

- 副标题：从业务意图到受控行动，从执行结果到可治理演进。
- 缩略结构：意图与结果层、中枢编排层、业务执行与技能层、上下文与记忆层，以及反馈闭环和控制保障面。

### 2. 先分清三种架构视图

- 系统运行视图回答：目标如何被接收、规划、执行、治理和反馈。
- DDD 领域视图回答：规则、状态、数据和公开语言归谁所有。
- 代码依赖视图回答：源码依赖方向和技术实现放在哪里。
- 三种视图分别表达，再通过契约、端口和事件建立对应关系。

### 3. 目标运行架构：四层主链路 + 两个横切系统

- 意图与结果层接收主体、业务目标、预期结果、约束和引用，并交付结果、证据和待确认事项。
- 中枢编排层基于受控上下文完成规划、分派、运行协调、恢复和结果汇总。
- 业务执行与技能层由智能体、真人或企业能力执行步骤；所有副作用通过受治理能力契约。
- 上下文与记忆层提供统一受治理的查询与快照装配，来源 Context 继续拥有原始事实。
- 控制保障面在关键节点强制检查，反馈闭环消费结果和证据；两者都不是调用链末端的普通服务。

### 4. 端到端规范主链路

- 主体、目标和约束形成 `IntentEnvelope`。
- `ContextQuery` 返回带权限、来源、版本、缺失项和过期策略的 `ContextSnapshot`。
- `WorkIntent → WorkflowPlan → WorkflowRun` 建立计划和运行实例。
- 步骤分派给智能体、真人或 `Capability`，执行后返回结构化结果和证据。
- `ResultEnvelope` 向调用方交付产物、引用和待确认事项。
- 业务结果和人工反馈只能形成改进候选；候选经过评估、必要审批和版本发布后才能进入生产。

### 5. 中枢编排层：逻辑角色不等于 DDD Context

- 运行角色包括监督者、任务拆解/规划、路由/分派和结果汇总。
- 工作规划拥有 `WorkIntent`、`WorkflowPlan`、规划策略和计划校验。
- 工作流运行拥有 `WorkflowRun/WorkflowStep`、DAG、租约、重试、恢复和真人停点。
- 任务管理拥有 `TaskCard` 的分配、汇报、验收和驳回生命周期。
- 来源业务 Context 拥有业务规则、原始事实和最终业务生效决定。
- 编排层不得直接读取其他 Context 的 ORM、直连供应商 SDK，或绕过权限、幂等和审批。

### 6. 业务执行与技能层：三类执行路径

- 智能体执行使用版本化专家快照；需要产生行动时调用能力执行门禁，无需能力调用时可直接返回执行结果。
- 真人任务由任务管理负责分配、汇报、验收和驳回，不经过能力执行门禁修改任务状态。
- 直接能力步骤由工作流运行发起 `CapabilityInvocation`。
- 能力执行统一校验主体、能力版本、参数、数据范围、风险、审批凭证和幂等记录。
- 业务 Context 用例、连接器执行、受治理数据查询、交付物和协作请求属于能力目标；HTTP、MCP 和沙箱只是技术适配。

### 7. 上下文与记忆系统：统一受治理入口

- 提案、会议、工作流、任务、会话和运营分析等来源 Context 各自拥有原始事实和写入规则。
- 环境投影围绕一次任务接收 `ContextQuery`，组合组织、专家、Wiki、检索、语义目录、组织记忆、数据查询和访问控制结果。
- 输出 `ContextSnapshot`，携带主体范围、来源引用、版本/时间、用途、缺失信息、敏感级别和过期策略。
- 模型生成的推断、摘要和建议必须标注类型与置信度，不能自动升级为企业事实。

### 8. 控制与安全保障面：六个强制控制点

- 能力对齐链：主体身份 → 角色/属性策略 → 数据范围 → 能力编号与版本 → 风险/副作用 → 审批要求 → 凭据范围 → 证据/审计。
- 控制点覆盖意图接入、计划生成、能力执行、外部副作用、结果交付和反馈升级。
- 高风险动作默认 `fail closed`。
- 人工审核只记录审核请求和决定；来源 Context 必须重新校验状态、不变量和审批版本后，才能执行生效动作。
- 审批通过不等于业务动作已经成功。

### 9. 反馈闭环：从业务结果到受控版本发布

- 反馈来自业务指标、真人验收/修正和执行失败/异常信号。
- 标准链路：真实结果 → 评估与归因 → 改进候选 → 影子评估 → 必要审批 → 所有者发布新版本。
- Prompt/专家策略、模型路由、SOP/知识、能力定义和访问策略分别回到自己的 Context 发布。
- AI 质量评估只能建议和验证，不能跨 Context 自动修改生产配置。

### 10. 业务场景一：运营分析

- **当前实现**：Excel 上传或 ThinkingData 同步 → `ops_daily_metric` 幂等写入 → 规则异常检测 → AI 生成运营日报/异常告警播报 → 结构化建议文本留痕。
- 当前建议仅保存在 `AgentTaskRecord`，不会创建 `ProposalCard`、`TaskCard`，也不会自动启动执行。
- **目标接续**：管理者判断是否需要行动 → 正式业务用例创建提案或任务卡 → 任务执行和真人验收 → 运营结果写回。
- 目标接续目前尚未在代码中自动打通。

### 11. 业务场景二：提案管理

- 创建提案后的初始状态是 `draft`。
- 发起 AI 预研时先进入 `researching`，模型输出经内部反思和必要修订后保存 AI 评审记录，并进入 `reviewed`。
- 内部反思不是独立业务状态。
- 真人评审只接受 `reviewed`，并把状态写成 `approved` 或 `rejected`。
- AI 无权写入 `approved/rejected`。
- `rejected` 当前禁止再次 AI 预研；只有 `approved` 能转换一次 `TaskCard`。

### 12. 业务场景三：会议管理

- 会议状态为 `scheduled → in_progress → closed`，也允许 `scheduled → closed`；`closed` 是终态。
- 真人/AI 发言和真人/AI 投票必须在 `in_progress` 状态执行。
- AI 生成纪要只要求至少已有一条发言，不强制会议仍处于进行中。
- 创建决议草案只校验会议存在。
- 真人票和 AI 票分开统计；`human_passed` 只是统计值，不会自动确认决议。
- 当前没有“投票 → 纪要 → 决议”的强制顺序状态机。
- 只有 `is_confirmed=true` 且尚未转换的决议可以创建一次 `TaskCard`。

### 13. DDD 分类：业务场景域、基础底座域、Platform 与 Bootstrap

- 业务场景域：提案管理、会议管理、运营分析。
- 基础底座域：知识、组织能力、执行、集成数据、沟通、治理和 AI 运营等具有独立业务语义和生命周期的 Context。
- Platform：数据库、Outbox、HTTP/MCP 运行时、LLM Gateway、缓存、对象存储、沙箱、安全机制和可观测性等技术实现。
- Bootstrap：应用入口、生命周期、依赖装配、Worker 和 Handler 注册。
- 任务管理与能力执行属于 Foundation Context；MCP 传输和 LLM SDK 属于 Platform。

### 14. 实施状态：模块化单体渐进迁移

- 阶段 0 已完成：四层运行架构、两个横切系统和 DDD Context Map 已分离。
- 阶段 1 已完成首版：静态 import 边界测试已建立，兼容入口仅在仍有历史调用方时保留。
- 阶段 2 进行中：Bootstrap、数据库、Outbox 和 HTTP 运行时已落地。
- 阶段 3～4 部分开始：受治理数据查询和提案领域层/应用层边界已开始迁移。
- 阶段 5～8 待按业务增量执行：规划、运行、任务、知识、治理和业务 Context 继续迁移。
- 最终判断标准：一个事实只有一个写入所有者；高风险动作可授权、可审批、可审计；结果可回溯；反馈不会形成在线自修改。
