# 14 · 任务编排层设计（Durable Runtime）

> 状态：已实现（2026-07-20）。本文是复合任务、异步执行、人工停点与未来 LangGraph adapter 的统一事实源。

## 1. 目标与边界

复合任务必须先形成可追踪的 DAG，再由后台 worker 推进；HTTP/SSE 入口只负责规划、提交事务和返回进度快照。
AI 只有建议与辅助执行权，资金、人事、项目、重大业务调整等红线步骤必须停在 `waiting_human`，真人验收后才会写入 resume outbox。

本阶段不引入 Celery、Temporal 或 LangGraph。LangGraph 后续可以替换规划/推进 adapter，但不能绕过以下边界：

- PostgreSQL 中的 `WorkflowRun/WorkflowStep/WorkflowEvent/OutboxEvent`；
- `ToolExecution` 幂等记录与确定性外部对象路径；
- `TaskCard` 人机界面镜像及真人验收权限；
- workflow/step/attempt/trace 全链路追踪。

## 2. 运行时模型

| 模型 | 责任 | 事实语义 |
|---|---|---|
| `WorkflowRun` | 一次复合任务实例、计划、父卡镜像、父状态 | `queued/running/waiting_human/succeeded/failed/cancelled` |
| `WorkflowStep` | DAG 步骤、依赖、attempt、version、lease、输入/输出 | `queued/running/waiting_human/succeeded/failed/cancelled` |
| `WorkflowEvent` | 追加式状态/抢占/重试/人工事件 | 不更新、不覆盖，只追加 |
| `OutboxEvent` | 与业务状态同事务写入的可靠命令 | `pending/processing/done/failed` |
| `ToolExecution` | 外部副作用幂等键、请求、结果、错误 | `pending/running/succeeded/failed` |
| `TaskCard` | 兼容 API、UI、人工审批镜像 | 不再作为执行真相源 |

步骤依赖以 `WorkflowStep.depends_on` 保存步骤 ID 列表；上游 `datasets/artifacts` 通过 `input_data` 注入直接下游。
每个步骤的逻辑副作用 key 为 `workflow_id:step_id:logical:<tool>:<action_index>`，attempt 单独记录，因此租约过期重试仍复用同一交付/协作结果。

## 3. 调用链路

### 3.1 提交（HTTP/SSE）

```text
desktop_chat / tasks API
  → orchestration_service.plan
  → WorkflowEngine.submit (当前 DatabaseWorkflowEngine)
  → workflow_service.create_workflow
      ├─ 父 TaskCard + WorkflowRun
      ├─ 全部步骤 TaskCard + WorkflowStep + depends_on
      ├─ workflow.created WorkflowEvent
      └─ workflow.advance OutboxEvent
  → 一个事务 commit
  → workflow_service.progress 返回 queued 快照
```

任何步骤、依赖、镜像或 outbox 写入失败都会由 use case rollback，不能留下半套编排。

### 3.2 worker 推进

```text
workflow_worker（轮询与生命周期）
  → OutboxEvent.pending / claim_next（event lease + 条件更新）
  → workflow_event_handler 路由 workflow.advance / workflow.step.execute
  → workflow.advance 计算 ready_steps 并为 ready step 入队
  → workflow_step_executor.claim_step_result（claimed/busy/terminal）
      ├─ busy：defer 原事件到 step lease 结束，不消耗 retry attempt
      └─ claimed：提交租约后再执行外部调用
  → run_agent(ExecutionContext)
  → ToolDispatcher.dispatch_text / dispatch(SkillRequest)
      ├─ collab：咨询或创建真人复核请求
      ├─ data_query：SQL 护栏 + datasets
      └─ deliver：Deterministic Deliverable/object path
  → complete_step（仅当前 lease/attempt 可写）
  → pipe_outputs + workflow.advance outbox
  → refresh_run_status + TaskCard 镜像同步
```

worker 的长调用由独立 heartbeat 续租；进程消失时只允许新的 worker 抢占已过期 lease，已成功或等待真人的步骤不会被恢复扫描重置。

Worker 还按 `WORKFLOW_RECOVERY_SCAN_SECONDS` 周期调用 `workflow_recovery.requeue_expired_steps`，
每批最多 `WORKFLOW_RECOVERY_BATCH_SIZE`。补发 key 包含 step id 与 version，同一过期版本只生成一个
`workflow.step.execute`；扫描故障只记录日志，不阻断普通 outbox 轮询。

### 3.3 真人停点

```text
WorkflowStep waiting_human
  → TaskCard reported
  → authenticated human POST transition accepted
  → accept_human_step
  → step.succeeded + step.human_accepted WorkflowEvent
  → workflow.advance resume OutboxEvent（同一事务）
  → HTTP 返回；下游由 worker 执行
```

审批动作不暴露给 AI skill registry；HTTP 入口仍走权限、状态机和 audit 记录。

## 4. 事务与并发规则

1. repository/service 默认只 `flush`；提交由 API/use case/worker handler 明确负责。
2. 步骤抢占使用 `WHERE id AND version AND (queued OR expired lease)`，更新行数不是 1 就视为未抢到。
3. 当前 lease owner + attempt 才能完成步骤；旧 attempt 的迟到回写会被拒绝。
4. outbox 使用 `dedupe_key` 唯一约束，多个 worker 同时计算 ready 只保留一条命令。
5. 重试次数、最后错误、下一次可用时间和 terminal failed 均持久化；耗尽后失败传播到步骤/WorkflowRun/父卡。
6. PostgreSQL 是 durable 队列真相源；Redis 只承担预算、熔断和短期共享状态。
7. `busy` 不是执行失败：事件只 defer，不能 complete，也不能增加 Outbox retry attempts。

## 4.1 模块责任

| 模块 | 责任 |
|---|---|
| `workflow_repository.py` | 创建/查询工作流与追加事件 |
| `workflow_state.py` | ready、claim/renew/complete、人工接受、输出管道 |
| `workflow_projection.py` | run 聚合状态、TaskCard 镜像、progress DTO |
| `workflow_recovery.py` | 过期步骤扫描与确定性补发 |
| `workflow_event_handler.py` | 事件类型路由与 complete/defer disposition |
| `workflow_step_executor.py` | heartbeat、Agent/Skill 外部调用与短事务落库 |
| `workflow_service.py` / `workflow_worker.py` | 兼容导出与生命周期 facade |

## 5. Typed Skill Runtime

`app/agents/contracts.py` 定义 `AgentRunner`、`ExecutionContext`、`SkillRequest`、`SkillResult`、`SkillExecutor` 与 `SkillDispatcher` 端口。`skill_registry.py` 管声明/提示词，`legacy_skill_adapters.py` 管旧中文文本协议，`tool_dispatcher.py` 管幂等调度，`skills.py` 仅保留兼容入口。
`ToolDispatcher` 负责：

- 结构化参数由目标 executor 的 Pydantic schema 校验；无注册的 `approve_*` 等生效动作直接拒绝；
- side-effect executor 在外部调用前写入 `ToolExecution`，成功结果可重放；
- 旧 `【咨询】/【发起协作】/【取数】/【交付】` 文本由 legacy adapter 生成同一 `SkillRequest`；
- 咨询依赖注入的 `AgentRunner`，service 不再 import `app.agents.base`，避免 `base → skills → service → base` 环。

## 6. 未来 LangGraph 接入点

新增 `LangGraphWorkflowEngine` 时只需实现 `app/agents/workflow_engine.py` 的 `WorkflowEngine`（或 planner 子端口）：

- LangGraph 节点输出转换为 `PlanStepLike`/`SkillRequest`；
- checkpoint 可映射到 `WorkflowRun/WorkflowStep`，但不能成为第二套状态真相；
- 节点执行仍由当前 worker、lease、ToolExecution 和人工事件包围；
- 先做 POC 比较分支/并行/可视化收益，再决定是否启用，不把框架依赖提前写入核心 service。

## 7. 进度 API 语义

`GET /tasks/{parent_id}/orchestration` 返回持久化快照：`workflow_id`、`trace_id`、父状态、完成数、等待人工卡 ID，以及每步的 `status/attempt/last_error/output_data/task_card_id`。
初次提交可能只返回 `queued`；前端通过 SSE/轮询观察状态，不假设请求返回时 DAG 已执行完。
