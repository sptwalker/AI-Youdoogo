# 14 · 任务编排层设计

> 状态:设计稿（已评审通过,待实现）。本文只定设计,不含实现代码。
> 目标:AI 助理接到复合任务时,先编排出有序步骤序列再依序执行,步骤间自动传递产出,
> 彻底避免次序错误/遗漏;同时红线（真人验收）不被自动化绕过。

## 1. 背景与根因

**触发场景**:用户命令"把昨天运营数据生成一份运营日报,放到交付区",AI 只在聊天区回了数据,
没生成文档。

**根因（两份代码探查确认）**:
1. **产出传递缺口** —— `ProtocolResult`（`app/services/collab_protocol.py:63`）只有 `notes`（文本）
   + `consult_replies`（AI 文本记录）两个字段。取数的 `rows`（`query_skill.py:83` 局部变量）、
   交付的 `Deliverable.id`（`deliver_service.py:130`）都被字符串化后销毁,从不进返回值。
   **步骤间无数据管道**,第 2 步拿不到第 1 步产出。
2. **解读轮不执行指令** —— 取数闭环里数据在"解读轮"（`query_skill._interpret`）才回喂 AI,
   而那轮产出被"深度硬限 1 跳"挡住不再 execute,故 AI 在解读里写的 `【交付】` 从不执行。
3. **无步骤编排** —— `task_flow` 只有 `parent_id` 平铺子任务,无 step/order/depends_on,
   无"依序执行 + 自动推进"。

**结论**:这不是单点 bug,是系统缺"编排 + 产出管道"这层能力。

## 2. 现有地基（复用,不重造）

| 能力 | 位置 | 复用方式 |
|---|---|---|
| 任务卡 + parent_id 自引用 | `models/task.py:16-46` | 每个编排步骤=一张带 parent_id 的子任务卡 |
| 状态机 transition 统一入口 | `task_flow.py` + `task_service.py:105` | 步骤推进走 transition,天然留痕 |
| 全程留痕 TaskCardLog | `models/task.py:49` | 每步状态变更一行,编排过程可追溯 |
| 单卡执行器 run_task | `scheduler.py:31` | 逐步驱动子任务卡执行 AI |
| 技能执行 execute_all | `skills.py:105` | 步骤内调技能（取数/交付/协作） |
| 红线 require_human 验收 | `deps.py:49` + `tasks.py:86` | 编排到红线步骤停下等真人,不绕过 |

## 3. 缺失地基（本设计新增）

1. **步骤顺序/依赖** —— TaskCard 无 step_no/depends_on。
2. **编排实例状态** —— 状态机是单卡的,无"整个流程进度"概念。
3. **步骤间数据管道** —— ProtocolResult 无结构化载荷,产出降维成文本即丢。
4. **自动推进** —— run_task 推到 reported 就停,无"一步完成自动派下一步"。
5. **红线挂钩推进** —— 需在真人 accept 后触发下一步,而非自动跑到底。

## 4. 设计方案（分两层）

### 4.1 产出管道层（阶段 A · 先做,~1-2 天）

给 `ProtocolResult` 加**结构化载荷**字段（面向"下一步输入",区别于面向"显示"的 notes）:

```
datasets:  list[QueryResult]      # 取数产出:columns/rows/sql/row_count
artifacts: list[DeliverableRef]   # 交付产出:deliverable_id/file_name/format/storage_path
```

- `query_skill.execute` 把 `rows` 结构化塞进 `datasets`（不再只字符串化）。
- `deliver_service.execute` 把 `Deliverable.id/file_name` 塞进 `artifacts`。
- `execute_all`（`skills.py:128-130`）扩展合并这两个新字段。

**修当前 bug（阶段 A 内即可闭环）**:
- 取数"解读轮"放行 `【交付】`/`【协作】`（仍禁 `【取数】` 防递归）——即 `_interpret` 产出再跑一次
  非取数技能。这样"取数→拿真实数据→同轮交付日报"一句话打通。
- 解读轮 prompt 透传用户原始意图（"要日报文档"）,AI 才知道要交付而不仅解读。

> 阶段 A 做完,用户最初的痛点即解决,且为阶段 B 铺好数据管道。

### 4.2 任务编排层（阶段 B · 大工程,另立里程碑）

**TaskCard 扩展**（迁移加字段,不破坏现有卡）:
- `step_no: int | None` —— 子任务在父编排下的序号（0=首步,展示排序用）。
- `depends_on: JSONB` —— 依赖的前序步骤卡 id **列表**（DAG:一步可依赖多步,无依赖=可立即执行）。
- `step_input: JSONB` —— 被依赖步骤的产出（datasets/artifacts 引用）注入本步的输入。

**新增 `orchestration_service.py`**:
1. **判断复合任务（仅多动作时规划）** —— 助理收到请求先轻量识别是否含多个动作。单动作直接走原路,
   **不进规划**（省成本、不影响普通问答）;仅识别到多动作才过一次 LLM 规划调用,产出 **DAG 步骤序列**
   （每步:做什么 + 用哪个技能 + depends_on 哪些步）。
2. **建步骤卡** —— 按 DAG 建带 step_no/depends_on 的子任务卡（复用 `task_service.decompose` 思路）。
3. **DAG 调度驱动** —— 拓扑推进:依赖全部完成的步骤才可执行;无依赖步骤可并行起。每步产出写入下游步骤的
   step_input。首版并行度可为 1（串行执行拓扑序,DAG 结构先立住）。
4. **红线停点** —— 步骤含资金/人事/项目等红线动作 → 该步推到 reported 后**停下等真人 accept**,
   真人验收（require_human）后 DAG 才解锁其下游步骤。绝不自动跨红线。
5. **编排进度** —— 父任务卡 status 聚合子步骤进度;TaskCardLog 记每步流转。

**接入点**:`desktop_chat_service` 识别多动作请求 → 起编排;进度以**折叠「任务进度」卡片**在对话流呈现
（一张卡展示 DAG 各步状态:待执行/执行中/等真人/完成/失败,可展开看每步产出;不逐步刷屏）。

## 5. 红线合规（贯穿）

- 编排只是把步骤**排序 + 自动串接**,不新增任何"生效权"。
- 任何红线步骤（资金/人事/项目/决议）仍走 `require_human` 真人验收,编排在该步停下,不自动跨越。
- 取数只读、交付只是文件、协作进复核队列——三个技能本身的红线约束不变。
- 全程 TaskCardLog + audit_log 留痕:谁发起、几步、每步产出、哪步等真人。

## 6. 分期与验收

**阶段 A（地基 + 修 bug,先做）**
- ProtocolResult 加 datasets/artifacts;query/deliver/execute_all 填充合并。
- 解读轮放行 deliver/collab（禁 data_query）,透传原始意图。
- 验收:桌面对话"把昨天运营数据做成日报放交付区" → 助理取数→拿数据→交付 xlsx → 交付区出现文件。
- 测试:query/deliver 结构化产出单测 + 取数交付闭环端到端。

**阶段 B（编排层,另立里程碑）**
- TaskCard 加 step_no/depends_on(JSONB 列表,DAG)/step_input + 迁移。
- orchestration_service:多动作识别→规划 DAG→建步骤卡→拓扑驱动→产出喂下游→红线停点。
- 接 desktop_chat；编排进度以折叠「任务进度」卡片呈现（前端新增进度卡组件）。
- 验收:一句"生成运营日报并通知运营总监" → AI 规划 3 步（取数→做文档→发通知[红线,等真人]）→
  前两步自动完成、第三步停在真人复核队列;对话区出现一张可展开的任务进度卡。
- 测试:规划正确性、DAG 拓扑推进、步骤间数据传递、红线步骤强制停、失败步骤不连累后续留痕。

## 7. 已定决策

1. **步骤依赖 = DAG**（depends_on 为 id 列表,支持并行分支/多依赖；首版并行度可为 1,结构先立住）。
2. **规划触发 = 仅多动作时**（单动作不进规划,省成本;识别到多动作才过 LLM 规划）。
3. **过程呈现 = 折叠「任务进度」卡片**（一张卡展示 DAG 各步状态,可展开;不逐步刷屏）。
