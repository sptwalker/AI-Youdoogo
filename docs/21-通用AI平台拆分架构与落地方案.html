通用 AI 能力平台
拆分架构与落地方案

把知识库、LLM 网关、专家（Prompt / Skill / Tool）平台和 Workflow Runtime 从业务项目中逐步拆出，在不重写现有产品、不迁移运行中流程的前提下，形成可复用、可独立演进的 AI 平台。

Executive Summary

0. 执行摘要

本次拆分的本质不是“把一个单体变成五个仓库”，而是把当前混在一个进程里的 业务能力、AI 通用能力和运行时能力重新划定所有权，并通过稳定契约协作。

复核结论：有条件可行，综合可行性约 7/10。 保留 ai-youdoogo 作为产品业务核心和前端 BFF；建设 ai-model-gateway、ai-knowledge-service、 ai-expert-platform、ai-workflow-runtime 四个逻辑平台。 先在原项目内形成 Port / Adapter、数据所有权和运维门禁，再逐个切换到远程实现； 是否独立部署必须由容量、团队和故障隔离收益决定。
4逻辑平台

模型、知识、专家、运行时分别拥有契约和数据。

0跨库直连

首期可共用 PostgreSQL 集群，但必须独立 DB、账号和迁移。

2交互范式

即时结果走 HTTP/SSE，长任务与可恢复副作用走事件。

6迁移阶段

Phase 0 打底，之后逐个平台灰度拆出。

必须先拍板的五件事

  1. 按“领域所有权”拆，而不是按现有目录或技术组件拆。
  2. 知识服务负责索引与检索，并可保留通用知识问答；专家平台只使用 Search 组合复杂执行。
  3. 专家平台拥有 Tool / Skill 的定义与编排，业务工具实现仍由业务数据拥有者提供。
  4. Workflow Runtime 只理解通用流程状态，不理解任务卡、提案、专家等产品概念。
  5. 运行中流程不跨系统迁移：旧流程在本地跑完，只有新流程按开关进入远程 Runtime。

0A. 可行性分析与必要修正

领域拆分方向正确，现有代码也已经具备部分 Port、纯契约、Outbox、Redis、MinIO 和 CCE 部署基础； 但当前生产拓扑仍是单后端，不能把“四个逻辑平台”直接等同于“四个新微服务立即上线”。

7/10Knowledge

6/10Expert

Why Now

1. 为什么要做这次拆分

目前项目已经验证了知识检索、模型路由、专家执行和工作流的可行性，但这些通用能力与产品业务模型仍在同一个部署单元、数据访问和调用栈中。继续叠加功能，会让每一次业务修改都同时触碰 AI 基础设施。

当前成本

  • 业务发布与模型、知识、运行时发布绑定，回归面不断扩大。
  • 通用能力无法被下一个产品安全复用，只能复制代码或继续堆进当前项目。
  • Prompt、Skill、Tool、组织专家混在一个模型里，责任边界难以说明。
  • 工作流契约含业务字段，运行时无法成为真正通用的调度底座。
  • 模型 SDK 对象在进程内传播，阻止 LLM 能力通过网络独立提供。

拆分后的收益

  • 不同平台可独立扩容、发布、限流和核算成本。
  • 新产品只接契约，不复制底层实现和供应商适配代码。
  • 平台故障边界更清晰，可定义超时、降级、重试和熔断。
  • 专家资产可版本化发布，执行可复现、可审计、可回滚。
  • 业务团队聚焦提案、任务、会议等差异化能力。

为什么不能直接把文件夹搬出去

直接搬迁会得到“分布式单体”。 如果保留共享 ORM、远程数据库查询、双向同步调用和业务字段泄漏，仓库虽然分开了，但任何服务仍不能独立修改和发布，网络故障还会放大原来的耦合。

因此判断拆分是否成功，不看仓库数量，而看以下指标：

独立所有权

数据只有一个写入真源，其他系统持 ID 或投影。

独立发布

契约兼容时，服务升级不要求所有消费者同时发布。

独立失败

某平台故障时，调用方有明确的超时、降级与恢复路径。

Goals & Guardrails

2. 目标、非目标与架构原则

目标

  • 四个通用平台可被多个业务产品复用。
  • 每个平台有清晰 API、事件、数据和运行责任。
  • 现有功能可按场景、知识库、工作流类型或流量比例渐进迁移。
  • 迁移任一阶段都可以回退，不要求一次性重写。
  • 从第一版契约开始支持平台作用域、追踪、命令幂等和版本。

非目标

  • 不把所有模块都微服务化；产品业务仍保留模块化单体。
  • 不在第一阶段引入 gRPC、Service Mesh 或复杂多集群。
  • 不在拆分过程中同时重写所有 Prompt、工作流和前端交互。
  • 不迁移正在执行的工作流实例。
  • 不建立一个包含所有领域模型的“大 common 包”。

八条约束原则

1. 业务政策向内

产品业务规则留在 ai-youdoogo，通用平台只能通过公开契约被使用。

2. 数据归属唯一

禁止共享 schema、账号、ORM、跨服务 Join 和远程表直连；初期可共享物理 PostgreSQL 集群。

3. 契约与内部模型分离

OpenAPI / AsyncAPI DTO 不直接复用数据库实体或框架对象。

4. 同步链路有上限

只在用户等待即时结果时同步调用，避免超过 3 跳的调用链。

5. 长任务才异步

短事务命令可同步幂等执行；长耗时、高风险或需恢复的副作用才进入事件 / Runtime。

6. 发布资产不可变

Expert / Prompt / Skill / Tool 使用不可变 Release，运行记录固定版本。

7. 迁移采用替换式分支

同一 Port 同时支持 Local Adapter 与 Remote Adapter，由特性开关选择。

8. 失败是契约的一部分

每个调用都明确超时、重试、幂等、熔断、降级和补偿。

Target Architecture

4. 目标架构

浏览器默认只访问 AI-Youdoogo 的 BFF。BFF 负责产品聚合、最终授权和前端友好的 DTO；通用平台通过内部 API 与事件总线协作。

同步 HTTP / SSE异步事件（传输实现延迟决策）

依赖方向必须保持为有向无环图

ai-youdoogo ───────→ Expert Platform ───────→ LLM Gateway
      │                     │
      │                     └───────────────→ Knowledge Service ─→ LLM Gateway
      ├────────────────────────────────────→ Knowledge Service
      └────────────────────────────────────→ Workflow Runtime

Workflow Runtime ── event: step.ready ──────→ Expert Platform
Expert Platform ─── event: step.completed ─→ Workflow Runtime
Expert Platform ─── capability request ────→ Business Capability Provider

关键点：Runtime 与 Expert 之间使用事件交接执行，不建立相互同步调用；否则会形成调用环和级联故障。

Integration Model

6. 拆出去以后，服务间应该怎么调用

6.1 选择同步还是异步

HTTP / JSON / SSE

同步调用

仅用于调用方必须立即拿到结果才能继续响应用户的场景。

  • 交互式专家对话与流式输出
  • 知识检索
  • 模型 Chat / Embedding / Rerank
  • 创建工作流并立即返回 run_id
  • 只读工具，以及可在 2–5 秒内完成的幂等短事务命令
Reliable Event Transport

异步事件

用于耗时任务、跨域状态传播，以及需要暂停、恢复、补偿或可靠重放的副作用。

  • 文档解析、分块、索引和回填
  • 工作流步骤就绪、完成、失败
  • 长耗时、高风险、依赖人工审批的业务工具调用
  • 执行结果、用量、审计与投影更新
  • 补偿、重试和死信恢复

6.3 Tool / Skill 的正确边界

专家平台管理“工具是什么、需要什么参数、风险等级和如何编排”，但不直接修改业务数据库。 真正的业务行为由数据拥有者实现为 Capability Provider。

Expert 选择工具根据 ToolDefinition、Skill 步骤和权限声明生成调用。
选择调用模式只读 / 短事务走 HTTP；长任务 / 审批型走事件。
业务服务复核资源拥有者重新鉴权、校验业务规则，不信任上游判断。
执行业务事务写业务数据和 Outbox，在同一数据库事务中提交。
返回确定结果同步响应或 completed / rejected / failed 事件，更新执行状态。

Platform Designs

7. 四个平台的详细设计

7.1 ai-model-gateway

统一模型接入、路由、限流、用量与供应商故障隔离。

01
负责
Chat / Embeddings / Rerank、模型卡、凭证、路由策略、候选切换、配额、用量、健康检查。
不负责
专家 Prompt、知识检索策略、业务会话、产品权限和任务流程。

首版 API

  • POST /v1/chat/completions：首版覆盖现有 system_prompt、user_message、temperature、同步 / SSE、usage 和 resolved_model。
  • POST /v1/embeddings：支持批量输入、模型维度与批次幂等。
  • POST /v1/rerank：输入 query + documents，输出稳定排序和分值。
  • GET /v1/models/policies/{key}：仅供管理与诊断，不向浏览器暴露密钥。

关键设计

  • 调用方传 model_policy_key 或语义角色，不直接绑定供应商名称。
  • 供应商密钥只存在网关密钥存储中，日志永不打印明文或完整 Authorization。
  • 现有 LangChain Adapter 留在网关内部，外部只看 JSON / SSE 契约。
  • Chat 的 request_id 只用于追踪，不承诺生成幂等；模型原生 tool_calls / JSON Schema 等能力按真实消费者需求再加入 v2。
  • 对生成、Embedding、Rerank 分别配置 Bulkhead，避免批量索引拖垮在线对话。

7.2 ai-knowledge-service

负责知识接入、解析、索引、检索和访问范围过滤。

02
负责
KnowledgeBase、Document、Chunk、IndexVersion、混合检索、RRF / Rerank、检索 ACL、来源追踪。
不负责
专家人格和复杂 Skill 推理、业务 Prompt、产品实体权限真源。

首版 API / Event

  • POST /v1/documents：登记上传并返回 document_id / ingest_job_id。
  • GET /v1/documents/{id}/status：查询解析与索引状态。
  • POST /v1/search：混合检索，必须传 tenant_key 与 visible scopes；project_ref 可选。
  • POST /v1/answer：可选的通用知识问答，保持当前知识库产品能力；专家执行不得反向依赖此接口。
  • knowledge.index.ready.v1 与 knowledge.index.failed.v1：索引状态事件。

关键设计

  • 文件正文放对象存储，事件只传 URI、hash 与元数据；跨服务访问使用预签名 URL 或最小权限 bucket/prefix 凭证。
  • 每次索引生成独立 index_version，便于蓝绿索引与快速回滚。
  • Search 返回原始片段、引用和分数；通用 Answer 可由 Knowledge 调 LLM Gateway，Expert 则直接使用 Search 自行编排。
  • 产品权限变化通过范围投影或检索时 scope 约束处理，避免复制整个产品授权模型。

7.3 ai-expert-platform

管理可复用 AI 专家资产，并执行 Prompt、Skill、Tool 与知识增强。

03
负责
Expert Definition / Release、Prompt Template、Skill / Tool Descriptor、执行编排、执行记录、评测和发布。
不负责
部门与汇报关系、业务工具的数据写入、通用工作流持久状态、模型供应商实现。

核心聚合

ExpertDefinition

可编辑草稿，描述用途、输入输出和资产绑定。

ExpertRelease

不可变发布快照，所有执行必须固定 release_id。

ExecutionRecord

记录 Prompt / Tool / Model / Knowledge 版本和追踪信息。

首版 API / Event

  • POST /v1/expert-executions：创建交互式或后台执行。
  • GET /v1/expert-executions/{id}/stream：SSE 输出。
  • POST /v1/experts/{id}/releases：发布不可变版本。
  • 消费 workflow.step.ready.v1，发布 expert.execution.completed.v1。
  • 短事务 Capability 使用同步内部 API；只有长耗时 / 审批型调用发布 Invocation 事件。

Skill 与 Tool

  • Skill 是声明式执行配方：步骤、输入输出 schema、可用工具、提示模板引用、失败策略。
  • ToolDefinition 是能力描述：key、version、schema、风险、权限声明、调用模式、provider_ref。
  • Tool Handler 不必都在专家平台；业务工具留在资源拥有服务，通用无状态工具可独立托管。

7.4 ai-workflow-runtime

只负责可靠推进通用流程状态，不理解任何产品业务名词。

04
负责
Definition Version、Run、Step、DAG、Lease、Retry、Timeout、Human Wait、幂等推进和进度事件。
不负责
任务卡、提案、专家快照、Prompt、业务审批规则、业务投影更新。

Runtime Contract v2

StartWorkflowV2

    "tenant_key": "youdoogo",

{

  "executor_ref": "expert-release:uuid",

关键设计

  • 所有产品 ID 放在 business_key 或 opaque payload 中，Runtime 不解析其含义。
  • 步骤通过 executor_ref 选择执行器；Runtime 只发布 step.ready，不同步调用专家。
  • 用 lease + heartbeat 防止 worker 永久占用；用 expected_version 防止并发旧写覆盖。
  • 业务系统消费进度事件形成自己的任务投影，不让 Runtime 反向写业务数据库。
Contracts & Consistency

8. 契约、数据一致性与版本治理

8.1 第一版契约的公共 Envelope

tenant_key

平台隔离键；当前由 Adapter 映射为固定 youdoogo。

project_ref?

可选业务引用；当前没有 project 聚合，不得设为必填。

trace_id

跨服务调用链关联。

request / event id

查询用于关联；事件和命令用于去重。

另外携带 actor_id、caller_service、schema_version； 事件增加 event_id、occurred_at 与 correlation_id。 idempotency_key 只要求出现在创建命令和副作用操作，不强加给纯查询或流式生成。

8.2 发布与兼容策略

  • 每个服务发布自己的 OpenAPI / AsyncAPI，并生成版本化客户端；不要手写散落的 requests 调用。
  • 内部领域模型与公开 DTO 分离，数据库实体永不作为网络契约。
  • 同一主版本只做向后兼容的字段追加；删除、改名、语义变化必须升主版本。
  • 消费者契约测试纳入 CI：Provider 变更必须验证所有已登记消费者。
  • 事件保留期必须覆盖最大故障恢复窗口，重要主题支持按 event_id 重放。

Production Readiness

9. 安全、稳定性与可观测性

身份与权限

  • 浏览器通常只拿产品 Token。
  • 第一远程服务前落地非对称短期 Internal JWT：iss、aud、service_id、actor、scope、exp≤5 分钟。
  • 平台只持验证公钥，不共享当前业务 HS256 JWT_SECRET；mTLS 作为后续纵深防御。
  • 传递 actor context，不传万能管理员凭证。
  • 资源拥有者执行最终授权。

秘密与数据

  • Provider Key 只在 LLM Gateway。
  • 日志脱敏 Prompt、Token、PII 和工具参数。
  • 对象存储按 tenant / service 前缀隔离，并启用 TLS 或仅限集群内网络。
  • 执行记录定义保留与删除策略。

稳定性

  • 所有外部调用必须超时。
  • 重试只用于可恢复且幂等的操作。
  • 按依赖设置 Bulkhead 与并发上限。
  • 熔断后快速失败或降级。

Migration Strategy

10. 总体迁移路线：先抽象，再绞杀

每个平台都按同一套路迁移：定义 Port → 保留 Local Adapter → 新建 Remote Adapter → 离线回放 / 受控对比 → 小流量切换 → 默认远程 → 删除兼容层。这样每一步都是可测试、可观察、可回退的。

每个平台统一的切换门禁

  1. 契约门禁：OpenAPI / AsyncAPI 版本通过消费者契约测试。
  2. 数据门禁：数量、hash、版本和抽样结果对账通过。
  3. 质量门禁：固定回放集、受控双跑或小流量 canary 满足预设指标；生成请求不得无预算地全量影子调用。
  4. 稳定性门禁：超时、熔断、限流、DLQ 和重放演练通过。
  5. 回滚门禁：特性开关和数据追平脚本在生产前实际演练。
关于双写：能不用就不用。优先采用“旧真源 Outbox 增量同步 + 批量回填 + 切换写真源”的方式。必须双写时，明确主写、失败补偿和对账，禁止两个服务同时被认为是真源。
Delivery Roadmap

11. 分阶段实施：一个个具体怎么做

当前 CI/CD 只支持前后端镜像，生产 CCE 又处于 Pod 上限，因此原估算偏乐观。 在 4–6 人团队下，完成 Phase 0 + LLM Gateway 约 6–9 周，继续完成 Knowledge 约 11–17 周； 四个平台全部独立生产运行顺序执行约 28–44 周。若有两支并行小队、专职平台运维并先完成集群扩容，可压缩到约 20–30 周。

Phase 0 · 边界与迁移底座

3–4 周所有远程化工作的硬前置
要做什么
  1. 登记四个平台的领域词汇、Owner、数据归属、禁止依赖和逻辑 / 物理部署边界。
  2. 完成 CCE Pod、CPU、内存、PVC、数据库连接数和迁移 Job 容量评估，给出扩容方案。
  3. 在现有项目为 LLM、Knowledge、Expert、Runtime 建立稳定 Port。
  4. 把现有实现包成 Local Adapter，保持行为不变；移除公开 API 中的 AsyncSession、ORM 和 LangChain 对象。
  5. 定义第一版 OpenAPI、错误码、公共 envelope、命令幂等规范；AsyncAPI 先定义语义，不绑定 Broker。
  6. 落地非对称 Internal JWT、统一 trace 和特性路由，禁止共享现有业务 JWT_SECRET。
  7. 定义 EventPublisherPort；先复用 PostgreSQL Outbox，完成 HTTP Relay + Inbox PoC，再决定是否引入 Broker。
  8. 设计独立 DB / 用户 / 迁移和对象存储 presign / prefix 授权；建立消费者契约与架构边界测试。
  9. 扩展 CI 服务模板，至少支持独立镜像、迁移、Secret、探针、回滚和漏洞扫描。
验收

业务用例只依赖 Port；Local Adapter 下全部现有测试通过；Internal JWT 可独立验签；容量方案获确认；首个远程服务模板能完整发布和回滚。

回滚

此阶段不改变运行拓扑，仅重构边界；按小提交回退即可。

Phase 1 · 拆出 LLM Gateway

3–5 周第一优先
要做什么
  1. 用现有 provider factory 和模型卡逻辑搭建网关内部 Adapter。
  2. 先按现有 LlmExecutionRequest 实现 Chat / Streaming parity，再增加 Embedding / Rerank、配额和 usage。
  3. 在 AI-Youdoogo 增加 RemoteLlmAdapter；Local / Remote 使用相同应用 Port。
  4. 先用固定录制样本和评测集验证；仅对低成本样本受控双跑，再切 Embedding / Rerank，最后切在线 SSE。
  5. 按 use_case 与流量 1% → 10% → 50% → 100% 灰度，观察首 token、成功率、成本和 fallback。
  6. 契约稳定后再建立独立仓库；只迁入网关拥有的代码，不复制业务角色、Prompt 或会话模型。
  7. 稳定后从业务服务移除供应商密钥和直接 SDK 依赖。
验收

网关可独立发布；业务代码不再创建 BaseChatModel；流式与非流式结果结构一致；供应商故障演练能在网关内切换候选。

回滚

特性开关切回 LocalLlmAdapter；本地密钥副本只保留一个明确截止日期的回滚窗口，之后从业务 Secret 中删除。

Phase 2 · 拆出 Knowledge Service

5–8 周第二优先
要做什么
  1. 复用现有 indexing / retrieval 契约，补 tenant_key、可选 project_ref、visible scopes、trace 和命令幂等。
  2. 建立独立逻辑 DB / 用户 / 迁移和向量索引；初期可共享 PostgreSQL 集群，不允许跨库查询。
  3. 继续共享 MinIO 集群但改用独立 bucket / prefix 凭证或预签名 URL；修复 secure 配置并演练对象读取。
  4. 批量回填文档元数据与索引，通过旧系统 Outbox Relay 同步新增 / 删除；原始对象可不重复复制。
  5. 用固定评测集比较旧 / 新检索：Recall@K、NDCG、零结果率、延迟与引用一致性。
  6. 先切只读 Search，再切新文档写入；按 knowledge_base 分批迁移。（读写两侧本地端口接缝均已就位：Search 见 ADR 0002·A1、Index 见 ADR 0006；此处仅剩远端 adapter 本体切换。）
  7. 保留通用 AnswerKnowledge；Expert Platform 只调用 Search，防止 Knowledge ↔ Expert 形成循环依赖。
验收

文档数、chunk hash、索引版本对账；检索质量不低于基线；Search p95 达标；权限越界测试为零。

回滚

Search 路由切回本地；远程新增文档通过事件回放至旧库；保留旧索引直到完整稳定周期结束。

Phase 3 · 拆出 Expert Platform

6–10 周模型与 Capability 拆分是重点
要做什么
  1. 把 ExpertProfile 拆为业务 OrgExpertMember 与平台 ExpertDefinition / ExpertRelease。
  2. 把 Prompt、模型策略、Skill、Tool Descriptor 迁成可版本化资产；建立草稿、评测、发布流程。
  3. 为当前每个专家生成不可变 Release，并在业务表保存 expert_release_id 映射。
  4. 实现 Expert Execute / SSE；内部调用 Knowledge Search 与 LLM Gateway。
  5. 建立 Capability Provider 协议；先迁只读和短事务同步工具，长耗时 / 审批型工具必须等待事件门禁通过。
  6. 以交互式专家为第一场景，后台步骤执行为第二场景灰度迁移。
验收

同一 release 可复现 Prompt / Tool / Model 配置；组织变更不生成 AI 资产版本；所有业务工具由资源服务最终鉴权，命令具备幂等和确定状态查询。

回滚

执行路由切回本地 Agent Runner；业务仍保留专家执行快照兼容字段，平台发布资产可导出为本地快照。

Phase 4 · 拆出 Workflow Runtime

8–12 周最后拆，依赖事件门禁
要做什么
  1. 发布 Runtime Contract v2，去掉 WorkflowPlan、ExpertExecutionSnapshot 和任务卡字段。
  2. 在 AI-Youdoogo 建立 Planning → Runtime v2 的 Anticorruption Layer，把 WorkflowPlan 翻译为通用 DAG + executor_ref + opaque input/output。
  3. 实现 Run / Step / Lease / Heartbeat / Retry / HumanWait / Outbox / Inbox。
  4. 先完成 Broker / Relay 的积压、重复、乱序、DLQ 和重放演练；门禁不过则 Runtime 保持本地。
  5. Runtime 发 step.ready；Expert 执行后发 completed / failed；业务系统消费进度构建任务投影。
  6. 新增 workflow_type 路由开关；只让新创建的流程进入远程 Runtime。
  7. 旧流程在本地 drain 到终态，监控无活动实例后再下线旧 worker。
验收

杀 worker、重复投递、网络分区、回执乱序和人工等待恢复演练通过；无永久卡死运行；业务投影可从事件重建。

回滚

停止把“新流程”路由到远程；已进入远程的流程继续在远程完成，不跨引擎迁回；必要时暂停新建并修复。

Phase 5 · 收口与平台化运营

3–5 周起持续治理
要做什么
  1. 确认旧流量、旧实例和回放窗口清空后，删除 Local Adapter 与兼容 Facade。
  2. 移除业务仓库中的供应商 SDK、向量索引实现、专家执行器和 Runtime 表。
  3. 建立版本淘汰、容量、成本、SLO、值班、灾备和租户配额机制。
  4. 选第二个产品接入，验证通用平台没有隐含 AI-Youdoogo 假设。
验收

四个平台可独立部署和恢复；第二产品无需复制实现；旧表和旧凭证按审计流程归档 / 删除。

回滚

删除兼容层前保留版本化制品、数据库备份与明确恢复手册；完成下线门禁后才执行不可逆清理。

Risks & Resourcing

12. 风险、取舍与资源建议

风险概率 / 影响预防措施触发后的处理
把现有耦合复制成分布式单体高 / 高Phase 0 先立 Port、数据归属和禁止依赖测试。暂停搬迁，回到契约和所有权重构。
同步调用链过长导致级联故障中 / 高用户链路最多 3 跳；Runtime / Expert 异步交接；Bulkhead。熔断、降级知识增强或切回本地适配器。
知识迁移后检索质量下降中 / 高固定评测集、受控双查、index_version 蓝绿。按知识库切回旧索引并重建新版本。
Tool 副作用重复执行中 / 高Invocation 幂等键、业务 Inbox、状态查询接口。补偿事务、人工审计，不盲目无限重试。
专家资产版本不可复现中 / 高不可变 Release，记录所有引用版本和模型解析结果。回退 release，冻结问题版本并重放评测。
Runtime 迁移出现双引擎状态冲突中 / 高不迁活动实例；run 创建时固定 engine。按 engine owner 继续完成，禁止跨引擎接管。
CCE 容量不足导致新服务无法安全发布高 / 高Phase 0 先扩容；为服务和迁移 Job 预留故障余量。停止物理拆分，回到同 Deployment 的逻辑边界。
把用户 JWT / 共享 Secret 当作服务身份中 / 高非对称短期 Internal JWT、audience 隔离和密钥轮换。撤销凭证、回退远程路由并审计 Token 使用。
误把本地 Outbox 当成跨服务消息总线中 / 高Relay / Inbox / DLQ / 重放故障演练通过后再拆 Runtime。长任务保持本地，停止启用远程事件消费者。
共享 MinIO root 凭证扩大泄漏面中 / 高独立 bucket / prefix 策略、预签名 URL、TLS 与凭证轮换。吊销服务凭证并按对象访问日志排查。
服务数量增加导致运维负担高 / 中统一模板、日志指标、部署方式；不急于引入复杂基础设施。合并低成熟度部署单元，但保持逻辑边界和独立数据。
团队同时建设导致契约漂移中 / 中平台 Owner、ADR、消费者契约测试和每周架构同步。冻结主干契约，先修兼容再继续功能。

Architecture Decisions

14. 建议固化的架构决策

产品业务保持模块化单体只拆具有明确复用价值、扩缩容差异和独立生命周期的 AI 通用能力。
禁止共享 schema、账号与 ORM初期可共享物理 PostgreSQL 集群；跨服务只通过 API、事件、对象存储引用或本地投影协作。
Knowledge 同时提供 Search 与可选 Answer通用知识问答留在 Knowledge；Expert 只依赖 Search，避免形成循环调用。
Tool 定义与 Tool Handler 分离专家平台拥有目录和编排，业务服务拥有业务副作用和最终授权。
Runtime 使用通用 Contract v2只理解 business_key、executor_ref、opaque payload 和运行状态。
HTTP/JSON + SSE 先行在实际性能证据出现前不引入 gRPC；异步消息使用可替换抽象。
消息中间件延迟到 Phase 3 决策先以 EventPublisherPort + PostgreSQL Outbox Relay / HTTP Inbox 验证；Runtime 拆分前再以吞吐、重放和运维能力选择 NATS 或现有 MQ。
服务身份不复用用户 JWT使用非对称短期 Internal JWT 与 audience 隔离，平台服务只持验证公钥。
运行中 Workflow 不迁移旧实例本地 drain，新实例创建时固定执行引擎，避免双真源。
采用 Branch by AbstractionLocal / Remote Adapter 并存，通过特性路由渐进切换和快速回退。
删除兼容层是最后一步先通过完整稳定周期、事件保留窗口和旧实例清空门禁。

技术基线假设

应用框架继续使用 Python / FastAPI；前端通过 AI-Youdoogo BFF 接入。
数据库每服务独立逻辑 DB、账号和迁移；初期可共用 PostgreSQL 集群。Redis 仅用于缓存、锁或限流，不作为业务真源。
文件S3 兼容对象存储；使用独立 bucket / prefix、预签名 URL 和可轮换凭证，数据库保存元数据与 hash。
消息首期 EventPublisherPort + PostgreSQL Outbox Relay / HTTP Inbox；Phase 3 前按实际需要选择 NATS 或现有 MQ。
身份浏览器 Token 只到 BFF；内部使用非对称短期 JWT，资源拥有者执行最终授权。
契约OpenAPI + AsyncAPI；生成客户端；Schema Registry 可在事件规模扩大后增加。
部署先扩容当前 CCE 并建立通用流水线；服务逻辑边界不强制等于首日的 Deployment 数量。
