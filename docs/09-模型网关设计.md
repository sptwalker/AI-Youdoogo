# 09-模型网关设计

> 版本：v1.0（2026-07-11）
> 定位：能力中台层「大模型网关」的详细设计与移植方案，对应 `app/llm/` 目录。
> 上游依据：docs/02-总体架构设计（能力中台层）、CLAUDE.md 技术栈表（唯一事实源）。

## 1. 目标与原则

模型网关是全系统唯一的大模型调用入口，所有智能体、知识库、会商模块统一经由 `app/llm/` 调用模型，禁止业务代码直接实例化模型客户端。

核心目标：

- **统一调用**：`create_llm(role)` 一个入口拿到可用模型实例，业务方无需感知供应商差异
- **自动降级**：主模型故障时按降级链自动切换（DeepSeek → Qwen → GLM），调用方无感
- **健康熔断**：对故障供应商按失败原因分级冷却，避免反复撞死墙
- **输出校验**：模型返回内容不合格时视同失败，触发切换
- **用量可观测**：首版用量记日志，阶段1入库并做日预算告警

设计原则：不自研 SDK、不做每用户密钥管理、不做首版用不到的负载均衡。国产模型均提供 OpenAI 兼容接口，全部走 `langchain_openai.ChatOpenAI + base_url`，一套代码适配所有供应商。

## 2. 复用来源与落位

网关整体移植自 **Bottleneck-Hunter 项目的 `llm_clients` 包**（已在生产环境验证的 factory / fallback / health / validate 四件套），落位到本项目 `app/llm/`：

| 本项目文件 | 来源 | 处理方式 |
|---|---|---|
| `app/llm/factory.py` | llm_clients/factory.py | 移植改造：密钥来源改环境变量，供应商表改为 DeepSeek/Qwen/GLM |
| `app/llm/fallback.py` | llm_clients/fallback.py | 基本原样移植（FallbackChatModel） |
| `app/llm/health.py` | llm_clients/health.py | 基本原样移植（ProviderHealth 内存熔断器） |
| `app/llm/validate.py` | llm_clients/validate.py | 基本原样移植（输出校验） |
| `app/llm/roles.py` | 新写 | 按本项目智能体角色重写角色→模型映射 |

移植时的删改清单见第 5 节。

## 3. 架构设计

### 3.1 调用链

```
业务代码（agents / services / knowledge）
        │  create_llm(role="ops_director")
        ▼
app/llm/roles.py      角色 → 模型偏好（主模型 + 降级链）
        ▼
app/llm/factory.py    create_llm 统一入口，按偏好组装
        ▼
app/llm/fallback.py   FallbackChatModel（包一层，串联候选模型）
        │ 每个候选 = langchain_openai.ChatOpenAI(base_url=供应商地址)
        ├── 调用前问 health.py：该供应商是否处于冷却期？是则跳过
        ├── 调用后过 validate.py：输出不合格 → 记失败、试下一个
        ▼
DeepSeek → Qwen(DashScope) → GLM(智谱)   顺序尝试，首个成功者返回
```

### 3.2 供应商接入表（全部 OpenAI 兼容模式）

| 供应商 | base_url | 模型 | 密钥环境变量 |
|---|---|---|---|
| DeepSeek（主力） | `https://api.deepseek.com` | `deepseek-chat` / `deepseek-reasoner` | `DEEPSEEK_API_KEY` |
| Qwen 通义（降级1） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus`（可调 qwen-max） | `DASHSCOPE_API_KEY` |
| GLM 智谱（降级2） | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus`（或当期主力版本） | `ZHIPU_API_KEY` |
| Claude（后期可选） | Anthropic 官方 SDK/兼容层 | 后期评估 | `ANTHROPIC_API_KEY` |

- 所有国产模型统一用 `langchain_openai.ChatOpenAI(model=..., base_url=..., api_key=...)` 实例化，无供应商专属 SDK。
- Claude 仅预留环境变量位，阶段3前不接入、不安装 anthropic 依赖。
- 依赖仅 `langchain-core + langchain-openai`（与 CLAUDE.md 一致；LangGraph 阶段3才引入，网关不依赖它）。

### 3.3 factory.py — create_llm 统一入口

```python
def create_llm(role: str = "default", **overrides) -> BaseChatModel:
    """按角色返回带自动降级的模型实例。

    1. roles.py 查角色偏好 → [主模型, 降级1, 降级2]
    2. 对每个候选构造 ChatOpenAI(base_url=..., api_key=settings.xxx)
    3. 包进 FallbackChatModel 返回
    """
```

- 密钥、base_url、超时、重试次数全部经 `app/core/config.py`（pydantic-settings）读取，禁止硬编码。
- 未配置密钥的供应商在组装时直接从候选链剔除，并 warning 一条日志（允许只配 DeepSeek 跑通开发环境）。

### 3.4 fallback.py — FallbackChatModel 自动故障切换

继承 `BaseChatModel`，持有有序候选模型列表：

- 按序尝试，捕获调用异常（网络错误、限流、鉴权失败、超时）
- 每次尝试前询问 `ProviderHealth.is_available(provider)`，冷却中直接跳过
- 成功 → 记 `ProviderHealth.record_success`，返回结果
- 失败 → 记 `record_failure(provider, reason)`，尝试下一候选
- 全链失败 → 抛出 `AllProvidersFailedError`，携带各供应商失败原因，由调用方（service 层）兜底转人工提示

### 3.5 health.py — ProviderHealth 内存熔断器

进程内内存字典，无外部依赖（首版单进程部署够用）：

| 失败原因 | 冷却时长（默认，可配置） |
|---|---|
| 限流 429 | 60 秒 |
| 超时 / 网络错误 | 120 秒 |
| 5xx 服务端错误 | 300 秒 |
| 鉴权 401/403（密钥错） | 3600 秒（基本等于本次运行内禁用） |
| 输出校验失败 | 30 秒（可能是偶发，短冷却） |

- 冷却期内 `is_available()` 返回 False，FallbackChatModel 跳过该供应商
- 任意一次成功调用即清除该供应商的失败计数
- ponytail: 内存熔断，多进程/多实例部署时需换 Redis 计数，届时再改

### 3.6 validate.py — 输出校验

对模型返回做最低限度合格性检查，不合格视同调用失败、触发降级：

- 空内容 / 纯空白
- 明显被截断（finish_reason 异常）
- 要求 JSON 输出的场景解析失败（由调用方传入 `expect_json=True` 等开关）

校验失败计入 health 的失败记录（短冷却），并在日志中留存原始返回片段供排查。

## 4. 角色 → 模型映射（roles.py）

| 角色 role | 主模型 | 说明 |
|---|---|---|
| `ops_director` | deepseek-chat | 平台运营部AI总监（首个落地部门智能体），日常分析与任务生成 |
| `data_analyst` | deepseek-chat | 数据分析/报表类任务 |
| `meeting_expert` | deepseek-reasoner | 会商智能体，深度推理、决策推演 |
| `default` | deepseek-chat | 未注册角色的兜底 |

- 降级链全角色统一：主模型 → `qwen-plus` → `glm-4-plus`。reasoner 降级到通用模型时能力有损，属可接受降级（保可用优先）。
- 新增部门智能体时只在 roles.py 加一行映射，不改其余文件。
- 温度等参数按角色给默认值（分析类 0.3、会商推理 0.7），业务方可 override。

## 5. 与源项目（Bottleneck-Hunter）的差异

| 项 | 源项目做法 | 本项目做法 | 原因 |
|---|---|---|---|
| 密钥管理 | 每用户加密密钥仓（数据库存储） | **删除**，全局密钥走环境变量：`DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` / `ZHIPU_API_KEY` / `ANTHROPIC_API_KEY`，经 `app/core/config.py` 读取 | 首批用户仅管理层3~10人，公司统一账号即可；符合开发铁律「密钥只走环境变量」 |
| 用量遥测 | SQLite 持久化 | **首版删除**，用量（角色、供应商、模型、token数、耗时、成败）走 logging 结构化日志 | 首版不需要查询分析，日志够用 |
| 用量入库 | — | **阶段1（已实现，迁移 004）** `llm_call_log` 表：role/model/token/耗时/成败 + **user_id/task_id 关联（已贯通 run_agent、知识库问答、提案预研、提示词优化）**；`app/llm/usage.py` 落库 + **日预算告警**（当日 token 超 `LLM_DAILY_TOKEN_BUDGET` 记 warning，飞书推送后续增量） | 对应原文档「大模型用量超标及时提醒」要求 |
| 供应商 | 源项目供应商组合 | DeepSeek / Qwen / GLM（+ Claude 预留） | 国产为主的模型决策 |
| roles.py | 源项目角色 | 按第 4 节重写 | 业务域不同 |

## 6. 冒烟与测试

| 文件 | 内容 | 何时跑 |
|---|---|---|
| `tests/test_llm_gateway.py` | 假模型（FakeChatModel）单测：主模型抛异常→自动切到降级模型并返回结果；全链失败→抛 AllProvidersFailedError；熔断冷却期内供应商被跳过；validate 空输出触发切换 | 每次 `uv run pytest`，不花钱、不联网 |
| `scripts/smoke_llm.py` | 真实冒烟：读 `.env` 密钥，对每个已配置供应商各发一条最小请求，打印 供应商/模型/耗时/首句返回；再走一次 `create_llm("default")` 全链验证 | 手动，接入新密钥或改网关后跑一次 |

验收标准：单测全绿；冒烟脚本至少 DeepSeek 成功返回；断开 DeepSeek 密钥后 `create_llm` 仍能经 Qwen 返回结果（人工验证一次降级）。

## 7. 阶段演进

| 阶段 | 网关能力 |
|---|---|
| 阶段0~1 | 本文档全部内容：四件套移植 + roles + 冒烟；阶段1加 `llm_call_log` 表与日预算告警 |
| 阶段2+ | 按需：流式输出接前端、按部门用量报表 |
| 阶段3+ | 编排采用**自研状态机**（`task_flow`+`scheduler`），智能体直接消费 `get_llm_for_role`/`create_llm` 产出的 BaseChatModel，网关无需改动；LangGraph 暂缓、Claude 接入后评估 |

## 8. Embedding（知识库向量化，网关外）

对话模型走本网关；**embedding 独立于网关**，在 `app/knowledge/embedding.py` 用 httpx 直连 OpenAI 兼容 `/embeddings` 端点（默认通义 `text-embedding-v3`，1024 维），密钥默认 `DASHSCOPE_API_KEY`。

- **A/B 可配置（已就绪）**：`EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` / `EMBEDDING_API_KEY` 三个 .env 变量即可换 bge-m3 等（须仍 1024 维，否则要改 `knowledge_vector.embedding` 列维度并重建 hnsw 索引）；**最终选型**待 bge-m3 端点 + 真实公司语料对比检索质量后定型
- 维度 1024 写入 `knowledge_vector.embedding`（pgvector）
- 未来若需 embedding 降级/多 provider 并行，可比照网关的 factory/fallback 思路扩展，届时再抽象
