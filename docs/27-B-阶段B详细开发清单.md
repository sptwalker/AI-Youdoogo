**关键事实（决定任务粒度）**：
1. 知识条目当前**无真人级归属**：`KnowledgeFile` 仅有 `uploader_id`（不参与过滤），检索唯一隔离轴是 `visible_kb_ids`；个人库 `KnowledgeBase.scope=personal` 的 owner 是 **agent_role 非真人**。→ B1 需补 per-item `owner_user_id` 才能「按真人隔离」。
2. AI 产出目前只落 `AgentTaskRecord`、**未 enqueue outbox**。→ B1 自动沉淀需在产出点补生产者 + 注册消费 handler。
3. 收件箱**没有可插入的表**，是 5 源现算投影。→「自动进收件箱」的正确姿势是**建一条来源聚合（Task）**，而非插收件箱行。
4. **无免打扰开关**（全库零命中），只有全局 `feishu_notify_enabled`。→ B2 需随 FocusSession 一起建专注期拦截。

## 二、迁移与 Context 分配

| 迁移 | 内容 | down_revision |
|---|---|---|
| `049_knowledge_base_owner` | `knowledge_base` 加 `owner_user_id`（可空 FK sys_user）+ 索引 `(owner_user_id)`；个人库归真人 | `048_inbox_item_state` |
| `050_time_management` | 新建 `schedule` / `focus_session` / `time_log` 三表（同一迁移）+ 各自 owner 索引 | `049_knowledge_base_owner` |

> **B1 隔离取舍（ponytail）**：不改检索热路径。个人知识 = **归真人的 personal-scope KnowledgeBase**，隔离复用**既有 `visible_kb_ids` 杠杆**（已贯穿两臂 + 契约 + local/remote adapter）。只加 `KnowledgeBase.owner_user_id` 一列 + get-or-create 个人库 helper；`index_text`/`search`/`answer` 全部照传现成 `knowledge_base_id`/`visible_knowledge_base_ids`，**零改 arms/contract**。API 层只放行「本人个人库 id」，跨人不可见。

- 新 Context：`app/contexts/business/time_management/`（照 project_management 分层）。ORM 行模型放 `app/models/time_management.py`。
- 无新表任务：B1 自动沉淀（用 outbox）、B3（用 Task/决议链路）、B4（纯前端）。

## 三、任务清单（单模块增量，逐项验收）

### B1 · 个人知识中枢

**B1.1　个人知识库归真人（复用范围隔离）**
- 落地：`app/models/knowledge.py` `KnowledgeBase` 加 `owner_user_id: uuid | None`（FK sys_user，nullable——公司/部门库留 NULL，个人库落本人）；迁移 `049` 加列 + 索引 `(owner_user_id)`。新增 helper `ensure_personal_kb(session, user_id)`：按 `owner_user_id==user_id & scope=personal` get-or-create（`code=f"personal:{user_id}"` 唯一）。
- 红线/隔离：个人库归本人；API 层只放行本人个人库 id → 跨人不可见（复用 `visible_kb_ids` 杠杆）。
- 测试：owner 落值 + get-or-create 幂等（重复调不建第二个）单测；迁移可回滚。

**B1.2　按真人隔离的「我的知识」检索/问答/推荐**
- 落地：`search_knowledge`/`answer_knowledge` 调用处传 `visible_knowledge_base_ids=(个人库id,)`——**零改 arms/contract**（现成范围过滤即真人隔离）。新增 `app/api/v1/` 路由：`/my-knowledge/search`、`/my-knowledge/ask`、`/my-knowledge/documents`（写入/列出本人条目），owner 一律取登录用户。
- 测试：本人只召回本人库；传他人库 id 被 API 拒（只放行本人）；未传 owner 的组织检索行为不回归。

**B1.3　经验自动沉淀（事件→个人库）**
- 落地：选**最有价值的一个事件源先接**（AI 任务产出：`agent_execution` recorder 落 `AgentTaskRecord` 处补 `outbox.enqueue`），注册 handler（`register_event_handler`）→ 调 `index_text` 写当前用户个人知识（`owner_user_id=产出归属人`）。
- ponytail：`# ponytail: 先接 AI 产出一个源，文档/纪要/复盘留 backlog，事件契约就位后追加 handler 即可`。
- 红线：写个人库属 `knowledge_index`（AUTOMATIC，内部辅助执行，不外发）；沉淀内容可编辑/删除。
- 测试：产出事件 → 个人库出现该条目（离线 mock outbox/handler）；幂等（dedupe_key 不重复沉淀）。

**B1.4　带来源的问答外壳**
- 落地：后端复用 `answer_knowledge`（已带 user_id）；新增/复用路由按 `owner_user_id` 限定「我的知识」问答。前端「我的知识」页：提问 → 答案 + 来源引用（hits 的 file/片段）。
- 测试：问答返回带来源；仅本人条目参与。

**B1.5　新建任务时 Top5 相关知识推荐**
- 落地：任务创建/编辑入口按「标题+描述」调 `search_knowledge(owner_user_id=me, top_k=5)`，返回 Top5 供前端旁栏展示（只读推荐，不自动改任务）。
- 测试：推荐只来自本人知识、Top5 截断。

### B2 · 智能日程与时间管理（新 `time_management` Context）

**B2.1　Context 脚手架 + 三聚合建表**
- 落地：照 project_management 建 `time_management/**`（public/domain/application{contracts,ports,use_cases}/entrypoints/infrastructure{composition,uow,repository}）；`app/models/time_management.py` 三 ORM；迁移 `050` 三表。
- 聚合：
  - `Schedule`（日程）：owner_id、title、start_at、end_at、source（manual/suggested）、status（**suggested/confirmed**/done/cancelled）、linked_task_id?。
  - `FocusSession`（专注/番茄钟）：owner_id、start_at、planned_minutes、status（active/completed/aborted）、intercept_notifications: bool。
  - `TimeLog`（时间记录）：owner_id、category、minutes、logged_date、ref_task_id?。
- 隔离：全部 owner_id，`_load` 命中他人 → `ResourceNotFound`（照 project_management）。
- 测试：三聚合 CRUD + owner 隔离单测。

**B2.2　智能排程「只出建议」**
- 落地：排程建议用例产出 `Schedule(status=suggested, source=suggested)`；用户 `confirm` 才转 `confirmed`（生效）。建议算法先固定规则（按任务 due/优先级填空档），`# ponytail: 固定规则排程，有行为数据后再上个性化学习（docs/27 §九）`。
- 红线：**建议态不占用/不通知**，真人确认才生效——对齐「涉及排期调整须真人确认」。
- 测试：建议态不视为已生效；confirm 后才 active；他人不能 confirm 我的建议。

**B2.3　专注番茄钟 + 通知拦截（单点）**
- 落地：`FocusSession` start/complete/abort 用例；在 `feishu_notify_person.send_to_recipient`（`operations.py:16`）**单点**加一道检查——收件人处于 active 且 `intercept_notifications=True` 的 FocusSession 则跳过发送（返回被拦截）。
- ponytail：`# ponytail: 拦截=专注期 best-effort 跳过点对点通知，不做补发队列；需要补发再加`。
- 红线：拦截只影响**发给本人**的通知，不改对外发送的红线停点。
- 测试：专注期内发给本人的通知被跳过；非专注期正常；对外发送红线不受影响。

**B2.4　周度时间复盘报告**
- 落地：按 `TimeLog` 聚合本周分类耗时，产出复盘（顾问型产出，写本人视图/收件箱，不外发）。`# ponytail: 先按 category 求和的周报，可视化延后`。
- 测试：跨周边界聚合正确；仅本人数据。

### B3 · 会议闭环增强

**B3.1　会后纪要待办自动进收件箱**
- 落地：**复用决议→任务链路**（`convert_resolution` 建 `task_type=resolution_execution` 任务 → 自动进收件箱 pending 投影）。若需「从纪要正文自动拆待办」，新增最小拆解用例（LLM 抽取候选待办 → 建 Task）；否则沿用决议链路零新增。
- ponytail：`# ponytail: 先沿用「决议卡→任务」既有闭环，纪要正文拆待办（自由文本抽取）留 backlog`。
- 红线：拆出的待办是**草稿任务**（真人可编辑/驳回）；不自动对外。
- 测试：闭会→纪要→（决议）→任务出现在收件箱投影。

**B3.2　会前推送（新钩子）**
- 落地：为即将开始的会议/日程产出「会前提醒」——写**本人收件箱（建自我提醒 Task）或自我通知**；若提醒**对外**（通知他人）则走 `waiting_human` 停点。
- 红线：对外会前通知**必停 `waiting_human`**（复用机械发布器红线）；自我提醒内部不停。
- 测试：自我提醒不停点；对外提醒停 `waiting_human`。

**B3.3　前端接线**
- 落地：会议视图接 `/minutes`、`/resolutions`、`/resolutions/{id}/convert` 端点；纪要/决议/转任务在前端可操作（真人确认）。
- 测试：前端 vitest 覆盖关键交互（转任务需真人点）。

### B4 · 视图补齐

**B4.1　时间线视图**
- 落地：新建 `frontend/src/pages/workspace/TimelineView.tsx`，AntD `Timeline` 竖向展示日程/任务按时间排列；`api/schedule.ts` 拉数。`index.tsx` 加 `'时间线'` tab（类型/options/分支三处）。
- 测试：vitest 渲染 + 空态。

**B4.2　日历视图**
- 落地：新建 `CalendarView.tsx`，AntD `Calendar` + `dateCellRender` 打点当日日程；点击查看/确认建议。`index.tsx` 加 `'日历'` tab。
- 测试：vitest 渲染 + 单元格打点。

## 四、红线矩阵（阶段 B 必守）

| 场景 | 能力/路径 | 红线处置 |
|---|---|---|
| 自动沉淀写个人库 | `knowledge_index`（AUTOMATIC） | 内部辅助执行，不外发；内容可编辑/删除 |
| 智能排程 | `Schedule.status` | **建议态 suggested，真人 confirm 才生效** |
| 番茄钟拦截 | 发给本人的通知 | 仅跳过本人通知，不改对外红线 |
| 会后待办 | 建草稿 Task | 真人可编辑/驳回；不自动对外 |
| 会前推送（对外） | 机械发布器 | **必停 `waiting_human`** |
| 个人数据 | 知识/日程/专注/时间 | 全 owner_id 隔离，命中他人 → `ResourceNotFound` |
