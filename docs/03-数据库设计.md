# 03-数据库设计

> 来源：《AI智能公司管理决策辅助系统-全套项目前置开发文档》之"03-数据库详细设计文档"，并按 2026-07-11 修订决策补充阶段0/1字段级DDL设计。
> 数据库：PostgreSQL 16（`timescale/timescaledb-ha:pg16` 单镜像，内置 TimescaleDB + pgvector）；ORM：SQLAlchemy 2.0 async + asyncpg；迁移：Alembic。

## 1. 数据库设计原则

- 范式设计，减少数据冗余，保证数据一致性
- 核心表统一基础字段：id、create_time、update_time、is_delete
- 业务关联清晰，外键约束合理，索引优化查询效率
- 时序数据、向量数据单独分层存储，适配AI检索与数据统计（同库分层：时序走 TimescaleDB hypertable，向量走 pgvector，不额外部署独立数据库）
- 表只在当前阶段用到时创建，禁止为未来阶段预建空表

## 2. 通用基础字段

所有业务表统一包含（对应 `app/models/base.py` 通用字段 Mixin）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键，默认 `gen_random_uuid()` |
| create_time | TIMESTAMPTZ | 创建时间，默认 `now()` |
| update_time | TIMESTAMPTZ | 更新时间，默认 `now()`，更新时刷新 |
| is_delete | BOOLEAN | 软删除标记（false 正常，true 删除），默认 false |

下文各表字段表格中省略以上四个通用字段，不再重复列出。

## 3. 核心数据表设计

> **当前基线**：Alembic 迁移 `001_baseline` 已建 `sys_user` / `sys_department` / `sys_role` 三表。其余阶段0/1表随对应模块开发时新增迁移。

### 3.1 用户权限模块表（阶段0，已细化）

权限首版简化为：**登录 + 3角色（admin / executive / member）**，角色直接以 `role_code` 冗余在用户表上；`sys_role` / `sys_department` 作为字典与组织结构表保留，为后续四级RBAC扩展（`sys_permission`、`sys_user_role`、`sys_role_permission`）预留扩展位——这三张关联表**首版不建**，需要时再加迁移。

#### sys_user 系统用户表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| username | VARCHAR(64) | NOT NULL, UNIQUE | 登录名 |
| password_hash | VARCHAR(255) | NOT NULL | bcrypt 哈希，禁存明文 |
| real_name | VARCHAR(64) | NOT NULL | 真实姓名 |
| role_code | VARCHAR(32) | NOT NULL, DEFAULT 'member' | 角色码，取值 admin/executive/member，逻辑关联 sys_role.code |
| department_id | UUID | NULL, FK → sys_department.id | 所属部门 |
| is_active | BOOLEAN | NOT NULL, DEFAULT true | 是否启用（禁用即不可登录） |

索引：`UNIQUE(username)`；`INDEX(department_id)`。首批用户为管理层 3~10 人，由 admin 后台创建，不开放注册。

#### sys_department 部门表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| name | VARCHAR(64) | NOT NULL | 部门名称（如"平台运营部"） |
| code | VARCHAR(32) | NOT NULL, UNIQUE | 部门编码（如 platform_ops） |

首个落地部门：平台运营部。

#### sys_role 角色表（字典表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| code | VARCHAR(32) | NOT NULL, UNIQUE | 角色码 |
| name | VARCHAR(64) | NOT NULL | 角色名称 |

初始字典数据（随迁移写入）：

| code | name |
|---|---|
| admin | 系统管理员 |
| executive | 高管/管理层 |
| member | 普通成员 |

### 3.2 智能体角色表（阶段1~2，字段级设计如下）

#### agent_role 智能体角色配置表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| name | VARCHAR(64) | NOT NULL, UNIQUE | 角色名称（如"运营AI总监"） |
| department_id | UUID | NULL, FK → sys_department.id | 所属部门 |
| duty | TEXT | NULL | 职责描述 |
| prompt_template | TEXT | NOT NULL | 系统 Prompt 模板 |
| permission_scope | JSONB | NOT NULL, DEFAULT '{}' | 权限范围（数据/操作边界） |
| tools | JSONB | NOT NULL, DEFAULT '[]' | 可用工具清单 |
| model_role | VARCHAR(32) | NOT NULL, DEFAULT 'daily' | 模型角色映射（daily→deepseek-chat / reasoning→deepseek-reasoner，见 docs/09） |
| is_active | BOOLEAN | NOT NULL, DEFAULT true | 是否启用 |

#### agent_task_record 智能体执行日志表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| agent_role_id | UUID | NOT NULL, FK → agent_role.id | 执行的智能体 |
| task_type | VARCHAR(32) | NOT NULL | 任务类型（daily_report/analysis/proposal/...） |
| input_summary | TEXT | NULL | 输入摘要 |
| output_content | TEXT | NULL | 输出内容全文 |
| tools_called | JSONB | NOT NULL, DEFAULT '[]' | 调用工具及参数摘要 |
| model_used | VARCHAR(64) | NULL | 实际命中的模型（含降级链结果） |
| status | VARCHAR(16) | NOT NULL, DEFAULT 'success' | success/failed/cancelled |
| error_msg | TEXT | NULL | 失败原因 |
| duration_ms | INTEGER | NULL | 执行耗时 |

索引：`INDEX(agent_role_id, create_time)`。所有AI操作必须留痕，满足"数据可溯源"红线；LLM token 用量首版记应用日志，不入库。

### 3.3 任务卡核心表（阶段2细化）

- task_card：任务卡主表（任务标题、类型、发起方、接收方、优先级、SLA、状态、依赖ID）
- task_card_log：任务流转日志表（每一步状态变更、操作人、时间、备注）

> 字段设计在对应阶段（阶段2）细化。

### 3.4 提案卡核心表（阶段2~3细化）

- proposal_card：提案主表（提案编号、部门、背景、方案、收益风险、优先级、状态）
- proposal_review：提案评审记录表（AI预研结论、人工评审意见）

> 字段设计在对应阶段细化。

### 3.5 会议决策表（阶段3~4细化）

- meeting_info：会议信息表（会议主题、时间、参会人、类型、状态）
- meeting_discuss：会议讨论记录表（发言内容、发言人、发言时间）
- meeting_vote：投票记录表（真人/AI投票结果）
- meeting_resolution：会议决议表（决议内容、落地任务、截止时间、负责人）

> 字段设计在对应阶段细化。涉及业务调整、资金、项目、人事的决议必须真人确认生效（meeting_vote/meeting_resolution 需区分真人与AI票并强制真人确认字段）。

### 3.6 知识库表（阶段1，字段级设计如下）

#### knowledge_file 文档文件表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| file_name | VARCHAR(255) | NOT NULL | 原始文件名 |
| category | VARCHAR(64) | NULL | 分类 |
| uploader_id | UUID | NOT NULL, FK → sys_user.id | 上传人 |
| storage_path | VARCHAR(512) | NOT NULL | MinIO 存储地址（bucket/object key） |
| file_size | BIGINT | NULL | 字节数 |
| mime_type | VARCHAR(128) | NULL | 文件类型 |
| status | VARCHAR(16) | NOT NULL, DEFAULT 'uploaded' | uploaded/parsing/indexed/failed |

#### knowledge_vector 向量索引表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| file_id | UUID | NOT NULL, FK → knowledge_file.id | 关联文档 |
| chunk_index | INTEGER | NOT NULL | 分块序号 |
| chunk_text | TEXT | NOT NULL | 分块内容 |
| embedding | VECTOR(1024) | NOT NULL | pgvector 向量列，维度以实际 embedding 模型为准（如 Qwen text-embedding-v3 为 1024） |
| source_ref | JSONB | NULL | 来源溯源（页码/段落/原文定位） |

索引：`UNIQUE(file_id, chunk_index)`；向量检索索引 `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`。建表迁移需先 `CREATE EXTENSION IF NOT EXISTS vector`。

### 3.7 业务时序数据表（阶段4细化）

运营数据、销售数据、研发进度数据、舆情数据、产能数据时序存储，用于AI趋势分析、异常监控。

> 字段设计在对应阶段细化。落地时按数据域建 TimescaleDB hypertable（`create_hypertable`，按时间分区），数据来源为飞书、内外部业务数据平台API、Excel/文档人工上传（接入方案见 docs/11）。

## 4. 数据库迁移规范

- 使用 Alembic 统一管理数据库版本迁移（`uv run alembic upgrade head`）
- 所有表结构变更必须生成迁移脚本，禁止手动改库
- 迁移脚本需可回退（提供 downgrade）；字典初始数据（如 sys_role 三行）随迁移脚本写入
- 生产环境数据变更必须提前备份
- 当前迁移基线：`001_baseline`（sys_user / sys_department / sys_role）
