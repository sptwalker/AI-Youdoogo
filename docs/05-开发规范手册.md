# 05-开发规范手册

> 2026-07-22 按 `docs/20-DDD领域边界与分层架构规范.md` 修订。技术栈唯一事实源为项目根目录
> `CLAUDE.md`；领域边界、数据所有权与 Context Map 以 docs/20 为准。

## 1. 项目目录规范

后端采用模块化单体。目录首先表达业务能力和依赖边界，不再以 `services/models/schemas` 横向分层作为目标结构。

```text
app/
├── bootstrap/                       # 唯一组合根
│   ├── app.py                       # FastAPI application factory
│   ├── lifecycle.py                 # 启停、资源释放、worker 生命周期
│   └── wiring.py                    # route/handler/adapter 注册
├── contexts/
│   ├── shared_kernel/                 # 极小跨 Context 契约，不得引入框架或传输语义
│   ├── foundations/                 # 多个业务场景复用的稳定业务能力
│   │   ├── knowledge/               # wiki/indexing/retrieval/semantic/memory
│   │   ├── workforce/               # organization/expert/capability/environment
│   │   ├── execution/               # agent/capability/planning/workflow/task/deliverable
│   │   ├── integration/             # connector management/execution/data query
│   │   ├── communication/           # assistant/group/collaboration
│   │   ├── governance/              # identity/access/review/audit/configuration
│   │   └── ai_operations/           # provider/usage/quality
│   └── business/                    # proposal/meeting/operational analytics
├── platform/                        # 无业务语义的技术机制
│   ├── database/
│   ├── outbox/
│   ├── http_runtime/
│   ├── llm_gateway/
│   ├── cache/
│   ├── realtime/
│   ├── object_storage/
│   ├── observability/
│   ├── security/
│   └── integrations/
├── api/                             # 迁移期 HTTP 兼容入口
├── core/                            # 迁移期配置/安全等兼容入口
├── models/                          # 迁移期 ORM 兼容入口
├── schemas/                         # 迁移期 HTTP DTO 兼容入口
├── services/                        # 迁移期兼容 facade，禁止新增业务实现
├── agents/                          # 迁移期 Agent runtime 兼容入口
├── knowledge/                       # 迁移期知识能力兼容入口
├── llm/                             # 迁移期 LLM gateway 兼容入口
└── integrations/                    # 迁移期供应商 client 兼容入口
```

域组目录只用于导航，不拥有模型、表或 Service。只有叶子 Context 可以拥有业务代码。例如
`contexts/foundations/integration/governed_data_query` 是 Context，`foundations/integration` 不是。
`contexts/shared_kernel` 不是新的业务 Context，只允许放经多个 Context 共同确认的极小稳定契约。

目录、表和服务只在当前需求真实使用时创建，禁止为未来阶段预建空壳。新增一级目录或新 Context 前必须先更新
docs/20 的 Context Map、数据所有权和公开能力。

## 2. Context 内部分层

复杂 Context 按需采用以下目录；没有真实职责时不得创建空层：

```text
<context>/
├── contracts/       # 对其他 Context 发布的稳定 DTO、event、facade/protocol
├── domain/          # Entity、Value Object、Aggregate、不变量、领域事件
├── application/     # command/query/use case、port、事务编排
├── entrypoints/     # HTTP、事件、Worker、CLI 等入站适配器
└── infrastructure/  # ORM、Repository、外部 client 等出站实现
```

依赖方向：

```text
Entrypoints ─→ Application ─→ Domain
Infrastructure ─────────────→ Application Ports / Domain
Bootstrap ──────────────────→ Context + Platform 具体实现
```

- Domain 禁止数据库、网络、环境变量、FastAPI、SQLAlchemy、Redis、httpx、LLM 和供应商类型。
- Application 定义自己需要的 port，禁止依赖 ORM、具体 Repository、FastAPI 或供应商 client。
- Entrypoint 只做输入解析、身份/参数校验、调用一个主要 use case 和输出映射。
- Infrastructure 实现 port，不得把 ORM/SDK 对象返回给内层，不得承载核心业务决策。
- Bootstrap 是唯一允许同时认识多个 Context 和具体 Infrastructure 的位置。

## 3. Context 间协作与数据所有权

1. 一个业务事实只有一个写入 Context；其他 Context 只保存 ID、不可变快照或自己的 read model。
2. Context A 禁止 import Context B 的 `domain/application/infrastructure`。
3. 同步协作使用调用方定义的 port，并由 adapter 调用对方 `contracts/facade`。
4. 异步协作使用“业务状态 + Outbox 同事务提交”，由 Bootstrap 注册下游 handler。
5. 禁止跨 Context 更新对方表、传递 ORM 或共享可变 Entity。
6. 跨 Context 默认最终一致；消费者必须处理重复、延迟、乱序和版本兼容。
7. Platform 禁止 import 任何业务 Context；业务 handler 不得放入 Platform。

## 4. 渐进迁移与兼容 facade

- 保持现有 API、表结构和 durable runtime 语义不变，以小步迁移替代整体重写。
- 迁移模块时，新路径成为唯一实现；仍有历史调用方时，旧路径只允许显式 re-export。
- 新模块禁止反向 import 旧 facade；调用方应逐步切换到 Context contract 或 Platform API。
- `app/services`、`app/models`、`app/schemas` 不再接收新的业务实现。
- 保留 facade 时必须增加身份测试或契约测试，证明旧导入仍指向新实现。
- 兼容 facade 删除前必须确认仓库内外调用方均已迁移。

当前首批落地：

- `app/bootstrap`：FastAPI 组合根；`app.main` 保留 ASGI 兼容入口。
- `app/platform/database`：DeclarativeBase、engine 和 session 生命周期。
- `app/platform/outbox`：OutboxEvent 及 enqueue/claim/lease/retry 持久化机制。
- `app/platform/http_runtime`：统一响应 envelope 与 FastAPI 全局异常处理。
- `app/contexts/shared_kernel`：只保留稳定、面向用户且与传输无关的应用失败分类。
- `Governed Data Query`：只读 SQL 护栏进入 Context application policy。
- `Proposal Management`：保留自己的领域/应用错误语言，由 Context entrypoint 映射 HTTP。
- 历史 `AppError` 调用已替换为 Shared Kernel 或所属 Context 的具体错误；
  `app.core.application_error` 与 `app.core.exceptions` facade 已删除。

## 5. 代码开发规范

- 遵循 PEP 8，使用 Ruff 自动格式化和检查。
- 全代码层提供 Mypy 类型注解；函数、类和公开接口必须有 docstring。
- 核心业务逻辑的注释说明设计理由、领域边界和异常条件，不重复代码字面行为。
- 禁止硬编码密钥、地址和配置；配置入口按 `CLAUDE.md` 与 System Configuration/Platform Config 边界执行。
- 数据库使用 SQLAlchemy 2.0 async；业务代码不得拼接原生 SQL。
- 外部 LLM、Tool、HTTP、对象存储调用不得持有长数据库事务。
- Repository 默认 `flush`，完整用例的 `commit` 由 Application/UnitOfWork 决定。

## 6. 测试规范

| 测试层 | 主要验证 | 真实依赖 |
|---|---|---|
| Domain unit | 不变量、状态转换、值对象 | 无 |
| Application use case | 编排、port、事务结果 | fake ports/UoW |
| Contract | DTO/event/facade 兼容 | 可选序列化器 |
| Infrastructure integration | ORM、并发、外部协议 | DB/mock server |
| Entrypoint | 参数、身份、错误映射 | FastAPI client |
| Architecture boundary | import 方向、循环、禁用依赖 | 静态 AST |
| End-to-end | 少量关键业务闭环 | 完整环境 |

提交前质量门：

```bash
uv run ruff check .
uv run mypy app
uv run pytest -q -m "not delivery_contract"
```

前端同时执行 `npm run test`、`npm run lint`、`npm run build`。

## 7. Git 协作规范

- `main`：生产稳定分支，禁止直接提交。
- `dev`：开发主分支。
- `feature/xxx`：新功能；`fix/xxx`：缺陷修复。
- 提交遵循 Conventional Commits：`feat/fix/docs/refactor/test/chore: 描述`。

## 8. 接口与安全规范

- REST 接口统一返回 `{code, msg, data}`，同时进行权限校验和参数校验。
- 外部输入必须防注入、防越权，并按最小权限访问数据。
- 敏感数据传输和存储必须加密，审计日志不得回显密钥。
- AI 输出可编辑、驳回和终止；业务调整、资金、项目和人事决议必须真人确认后生效。
- Human Review 只记录审核请求与决定；来源 Context 必须重新校验自身状态和不变量后执行生效动作。
