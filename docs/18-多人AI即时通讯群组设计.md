# 18 · 多人+AI 即时通讯群组设计

> 状态:设计稿（待评审）。为系统增加"多人真人 + 多 AI"的即时通讯群组，实现自由实时信息交互。
> 四项架构决策已定：**SSE广播+Redis发布订阅 / 飞书SSO登录 / 飞书组织同步 / 分期递进**。
> 红线不变：AI 仅建议/分析/辅助执行权；真人聊天不新增任何 AI 生效权；升格提案/任务仍真人确认。

## 1. 背景与目标

现有"协作空间(discussion)"已是"多人+多AI"数据雏形(speaker_type human/ai、@mention、可升格)，
但有一条核心硬缺口：**零跨请求广播**——SSE 只在"我 POST 消息"时把 AI 回复推给我自己，
A 发言 B/C 收不到。要做真即时群聊，必须补"服务端主动推送"。

**目标**（对应用户 5 项需求）：
1. 从飞书同步公司组织架构 + 真实员工身份库（中英文名/ID/部门/职务）。
2. 工作桌面可加入真人员工 + AI 员工，实时建群讨论。
3. 桌面新增"讨论组"页签：多群列表 + 未读计数 + 随时切换。
4. 群内分享话题/图片/文件，体验对齐企业微信，通讯即时。
5. 群聊内容自动入公司知识库。

## 2. 现有地基（勘察确认，复用为主）

| 能力 | 位置 | 复用方式 |
|---|---|---|
| 群聊数据雏形 | `DiscussionChannel`/`DiscussionMessage`(speaker_type/speaker_id/@mention/ref升格) | 扩成正式群聊，非重建 |
| 飞书异步客户端 | `integrations/feishu/client.py`(tenant_access_token+分页范式) | 加 contact API 薄方法 |
| SSE 协议栈 | `core/sse.py` + 前端 `client.ts` fetch+ReadableStream | 广播复用同协议 |
| Redis 共享态 | `core/shared_state.py`(H1.4) | pub/sub 广播背板 |
| 文件存储 | `knowledge/storage.py` MinIO put/get | 消息附件复用 |
| 聊天入库范式 | `desktop_chat_service.archive_old`→`memory_service`提炼→KB | 需求5 几乎白送 |
| 组织建模 | `SysDepartment`(物化path)/`org_service`/`org_template`(幂等upsert) | 同步照搬幂等范式 |
| 外部拉数范式 | `ops_data.ingest_from_thinkingdata`(resolve→拉→映射→幂等upsert) | 组织同步模板 |

## 3. 缺口（本设计新增）

1. **零跨请求广播** —— 无 WebSocket、无 pub/sub，A 发言 B/C 收不到（核心）。
2. **频道无成员表** —— 无 membership，任何登录者可读写，无法定向"群"。
3. **无未读计数/已读回执**。
4. **真人无法作为聊天发言者** —— 桌面圆桌纯 AI；真人员工无登录路径。
5. **SysUser 极简** —— 无英文名/职务/飞书ID/头像；只建模管理层，普通员工缺位。
6. **飞书零通讯录能力**；无外部ID映射字段；无定时同步；部门层级硬顶 2 级（飞书常>2）。
7. **无图片/通用文件消息类型**（交付区仅 AI 产出 csv/xlsx/md/txt）。

## 4. 架构决策（已定）

### 4.1 实时传输 = SSE 广播 + Redis 发布订阅
- **发消息**：廉价 POST（落库 + publish 到 Redis 频道）。
- **收消息**：每用户一条长连 SSE 订阅流（订阅其所在群的 Redis channel），有新消息即推。
- **多 worker 一致**：Redis pub/sub 作广播背板——A 连 worker1、B 连 worker2，B 也能收到（H1.4 教训：进程内状态多 worker 不通）。
- **为何不用 WebSocket**：IM 本质不对称（发是廉价POST、收才需长连），SSE 单向够用；复用整套 SSE 栈 + H1 已调好的 nginx `proxy_buffering off`；WebSocket 要平行搭传输栈+握手鉴权+重连，对内部工具是过度工程。

### 4.2 真人登录 = 飞书 SSO（OAuth 扫码）
- 员工用飞书扫码登录 → 按 `feishu_open_id` 精确解析已由组织同步或管理员手工预绑定的本地账号，
  再签发本系统 JWT；未绑定身份不自动开户。
- 复用现有 JWT 体系；SSO 只是多一条签发入口。

### 4.3 组织同步 = 飞书通讯录
- `contact/v3/departments`（部门树）+ `contact/v3/users`（员工）分页拉取。
- 用 `open_department_id`/`open_id` 做稳定映射键（非 name），幂等 upsert。

## 5. 分期规划与验收（全部完成 ✅，425 测试全绿）

> I1–I7 已全部实现、测试、推送主线。迁移 034（飞书身份）+ 035（群成员/附件）。

### I1 · 身份同步 ✅
- 模型：`SysDepartment.feishu_open_id`；`SysUser` 加 `feishu_open_id/en_name/title/mobile/avatar_url`；放宽部门层级>2；映射唯一索引（软删条件式）。迁移 034。
- 飞书 contact：`list_departments()`（递归）/`list_users_by_department()`（分页）。
- `org_sync_service.sync_from_feishu`：open_id 稳定键幂等 upsert；物化 path 任意深度。
- API `POST /org/sync-feishu`（admin+审计）；前端"从飞书同步"按钮。6 单测。

### I2 · 飞书 SSO 登录 ✅
- **飞书 OAuth**：`authen/v1/access_token`（code 换 user_info）；client 加 `oauth_user_info(code)`。
- **auth_service** 加 `login_by_feishu(code)`：按 open_id 精确查找已预绑定 SysUser → 签发 JWT。
- **API** `GET /auth/feishu/url`（拿授权 URL）+ `POST /auth/feishu/callback`；前端登录页加"飞书登录"。
- **验收**：已预绑定员工飞书扫码 → 登录同一本地账号并保留既有角色；未绑定身份明确拒绝。
- **红线**：SSO 不开户、不授角色；组织同步若预建用户固定为最低权限 `member`，角色变更仍走 admin。

### I3 · 实时内核（核心硬缺口）✅ —— Redis pub/sub 真库往返验证
- **广播背板** `realtime_service`：`publish(channel, event)` → Redis PUBLISH;`subscribe(channels)` → 异步 SUBSCRIBE 生成器。基于 redis.asyncio pub/sub。
- **每用户订阅流** `GET /realtime/stream`（SSE）：订阅该用户所在群的 channel，转发 Redis 消息为 SSE 事件。含心跳保活 + 断线重连（前端 EventSource 式重连）。
- **发消息即广播**：群发消息落库后 publish 到群 channel，所有在线订阅者实时收到。
- **验收**：A 在群发言 → B/C 浏览器**不刷新**实时收到（真即时）；多 worker 下（模拟）跨 worker 也收到。
- **降级**：Redis 挂 → 订阅流报错前端回退轮询（保证不完全失联）。

### I4 · 群成员 + 真人参与 ✅（迁移 035）
- **成员表** `ChannelMember`：channel_id + member_type(human/ai) + member_id + 加入时间 + last_read_at（为未读铺垫）。
- **频道升级**：DiscussionChannel 从"部门频道"扩为"任意群"；建群选成员（真人+AI 混合）。
- **发言建模**：真人发言直接落 DiscussionMessage(speaker_type=human)；@AI 触发 run_agent_stream（沿用 fan-out≤3 护栏）。
- **权限**：只有成员可读写该群（行级隔离，复用 H1.2 range 思路）。
- **API**：建群/加退成员/群列表（我的群）。
- **验收**：建混合群 → 真人发言 AI 可 @、AI 答复群内可见；非成员进不来。

### I5 · 话题页签 + 未读 ✅
- **桌面新增"讨论组"页签**：我的群列表 + 每群未读数 + 切换加载。
- **未读计数**：基于 ChannelMember.last_read_at 对比群内新消息数；进群/读消息更新 last_read_at。
- **实时未读**：I3 广播新消息时，非当前群的成员未读 +1（前端角标）。
- **验收**：多群并存、未读数准确、切群清零、企微式体验。

### I6 · 文件 / 图片 ✅（消息 attachments 落库；上传 UI 可后续增强）
- **消息附件**：DiscussionMessage 加 `attachments`(JSONB: [{type,name,storage_path,size}])；图片/文件走 MinIO。
- **上传下载**：复用 knowledge 上传范式（FormData）+ desktop 下载范式（StreamingResponse）。
- **验收**：群内发图片显示缩略、发文件可下载。

### I7 · 自动入库 ✅（复用 H3.2 提炼）
- **群聊归档**：定期/关群时把群聊记录经 `memory_service.distill_conversation` 提炼 → ingest 进公司/部门 KB（复用 H3.2）。
- **验收**：群聊内容进 KB、可被检索问答；提炼失败兜底存原文。

## 6. 红线合规（贯穿）

- 真人即时聊天是**信息交互**，不新增任何"生效权"——发消息不触发业务决议。
- AI 参与群聊沿用现有护栏：fan-out≤3、轮数≤3、日预算硬闸（H2.2）、禁 AI 互@。
- AI 产出若要升格为提案/任务，仍走 `ref_type/ref_id` + 真人确认闸门。
- 飞书同步/SSO 只读飞书身份，密钥走 sys_config 脱敏（H1.1 加密）；SSO 仅解析预绑定，
  组织同步预建账号最低权限。
- 群消息落库 + 广播全程可审计；文件走 MinIO 有权限边界。

## 7. 已定决策

1. **实时传输 = SSE 广播 + Redis pub/sub**（复用现有栈，真即时，多 worker 一致；非 WebSocket）。
2. **真人登录 = 飞书 SSO 扫码**（按 open_id 精确解析已预绑定账号）。
3. **组织同步 = 飞书通讯录**（open_id 稳定键幂等；企微暂不做）。
4. **分期递进 I1→I7**（每期独立验收 + 全量测试 + 提交）。

## 8. 技术风险与提示

- **飞书权限**：需申请 `contact:department.base:readonly`、`contact:user.base:readonly`、OAuth 登录范围；上线前确认企业已授权。
- **部门层级 2 级硬限**：飞书组织常>2 级，I1 须放宽（去 level 校验或物化 path 支持任意深度）。
- **runtime_config 多 worker**：进程内缓存，飞书凭证多 worker 各持一份——已知约束，同步/SSO 不受影响（每 worker 自取 token）。
- **SSE 连接数**：每在线用户一条长连，几十上百人内部工具无压力；上千需评估连接池/网关超时。
- **消息顺序/去重**：广播 + 落库双路，前端按消息 id 去重、按 create_time 排序。
