# 27 - 个人智能工作台开发规划书

> 文档版本：V1.0（评审稿）｜ 创建：2026-08-14 ｜ 状态：**待评审，未开工**
> 定位：把现有「个人桌面」（对话驱动的任务执行器）升级为「项目化个人智能工作台」。
> 与豆包 PRD 的关系：`docs/workspace/` 下的 PRD + 16 份分阶段提示词是**需求参考**，不是最终方案。
> 本规划书以 CLAUDE.md（技术栈唯一事实源）与现有代码现实为准，对 PRD 做**落地重构**。

---

## 零、结论先行（TL;DR）

1. **这不是新建子系统，而是「聚合 + 激活 + 前端外壳」升级。** 豆包 PRD 假设从零新建 `app/workspace/`
   （新 `workspace_` 前缀表、新 LangGraph、Elasticsearch）。但代码现实里，七大模块中约 **70% 已有归属
   Context**：`work_desktop`（当前桌面聚合器）、`task_management`（任务卡 + 状态机）、durable
   `workflow_runtime`+`work_planning`（AI 任务编排 + 真人停点）、`knowledge/*`（混合检索）、
   `operational_analytics`（指标 + 异常）、`group_messaging`/`assistant_conversations`/
   `collaboration_requests`（协同）、`meeting_management`、`report_scheduling`（定时）。
   直接照搬 PRD 的 `app/workspace/` 会**违反 docs/20 的 DDD 边界**（横向 facade 禁令、模型归叶子
   Context 所有），并与已收口的架构门禁冲突。

2. **真正的新建量集中在三处**：①「项目（Project）」聚合——现在**没有**任务分组的项目概念；
   ②「智能日程 / 专注 / 时间统计」——现在**完全没有**这一域；③「主动巡检调度器 + 每日仪式」——
   现在有定时基建（`report_scheduling`）但没有巡检用例。其余都是**扩展既有 Context + 前端外壳**。

3. **红线是本次升级最关键的治理裁决。** PRD 5.4「人机分工自动化」写着「AI 自动执行……员工只审核」
   且「用户可配置哪些类型任务 AI 可全自动执行**无需确认**」。这与 CLAUDE.md 红线
   **直接冲突**。裁决：**对外/涉及业务调整·资金·项目·人事的能力一律停在 `waiting_human`**；
   只有「内部顾问型产出」（不外发、notify=False）可自动。所谓「自动执行白名单」只能落在既有
   `AUTOMATIC_CAPABILITIES` 集合内，**不得开放给用户扩展到对外副作用**。

4. **技术选型全部回归 CLAUDE.md 唯一事实源**（详见第三章）：Python 3.12（非 3.11）、durable
   PostgreSQL runtime（非裸 LangGraph）、pg_trgm + pgvector 混合检索（非 Elasticsearch）、
   `foundations/knowledge/*`（`app/knowledge/` facade 已删）、`group_messaging` SSE + Redis
   pub/sub（非裸 `app/core/websocket.py`）、APScheduler/`report_scheduling`（非 Celery）。

5. **建议节奏**：把豆包的 4 期（6+6+6+4 周）重排为**与现状对齐的 4 个阶段**，第一阶段先做
   「统一任务抽象层收口 + 项目聚合 + 工作台前端外壳 + 收件箱增强」，跑通最痛的「任务管不过来」，
   其余按价值密度递进。**每阶段独立验收后再进下一阶段**（CLAUDE.md 单模块增量铁律）。

## 四、红线与治理对齐（最重要的一章）

> 红线（CLAUDE.md）：**AI 仅有建议权、分析权、辅助执行权；涉及业务调整、资金、项目、人事的决议
> 必须真人确认生效。**

PRD 多处描述「AI 主动」，需逐一收敛到红线内：

| PRD 描述 | 风险 | 收敛裁决 |
|---|---|---|
| 5.4「AI 自动执行……员工只审核」+「白名单无需确认」 | 越权对外/改业务数据 | 自动执行**仅限** `AUTOMATIC_CAPABILITIES`（内部顾问产出、notify=False、无外发）。**白名单不得用户扩展到对外副作用** |
| 4.1.3「批量处理：AI 预填 + 批量确认」「批量审批」 | 审批是决议 | AI 只做**预填 + 建议结论**；**每条审批仍需真人点确认**，批量确认=真人一次动作确认多条，非 AI 代批 |
| 4.2.3「一键催办发送任务卡给负责人」 | 对外发送 | 催办对外发送=对外副作用，走机械发布**停点后真人触发**或降级为**只在本人收件箱提示** |
| 5.2 巡检「立即打断 / 催办 / 联动调整排期」 | 自动改排期/对外催 | 巡检产出**只写收件箱/日报的预警与建议**；改排期、对外催办均需真人确认 |
| 4.6.2「讨论一键转提案 / 转 AI 任务」 | 转提案=生成决议草案 | 转 AI 任务（内部）可自动；**转提案生成的是草案**，进入既有提案审批流由真人核准 |
| 4.7.4「决策辅助卡：推荐方案」 | 决策 | 只产出**辅助卡（数据+方案+利弊+推荐）**，最终决策真人做、真人记录 |
| 5.5「个人日报一键同步上级」 | 对外发送 | 日报**生成**自动；**同步上级是对外发送，真人点发** |

**落地机制**：以上全部复用既有 `workflow_runtime` 的 2-Port 机械发布 + `requires_human_review`
停点范式（compose 红线停真人 → 机械 `*_publish`）。工作台**不新建**绕过停点的执行路径。

安全与日志铁律（继续沿用）：密钥经 `runtime_config.effective` / `sys_config` / `.env`，**禁硬编码**；
list 接口脱敏（末 4 位/hint）；日志**不打 token / 完整 URL / body / 收件人**，只记 host + `type(exc).__name__`。
个人数据（知识/任务/日程/指标卡）默认**仅本人可见**，行级隔离（`user_id`）——对应 PRD 6.2 与 docs/16 P0。

## 五、统一任务抽象层：关键设计裁决

### 5.1 状态机现实 vs PRD
现有任务卡状态机（`task_management/domain/state_machine.py`，**载重于 durable runtime 与红线停点**）：

```
created → dispatched → executing → reported → accepted / rejected
                                              rejected → dispatched / cancelled
（无 blocked，无 archived；terminal = accepted / cancelled）
```

PRD 5.1 想要的用户面泳道：`待启动 → 进行中 → 阻塞 → 待审核 → 已完成 → 已归档`。

### 5.2 裁决：**不重写核心状态机，加派生投影 + 两个正交维度**
- **不动**执行态状态机（它是 durable 编排 + 真人停点的不变量，重写风险极高、收益低）。
- **加一个纯函数看板泳道投影**：把执行态映射到用户面泳道
  （`created→待启动`、`dispatched/executing→进行中`、`reported→待审核`、`accepted→已完成`、`rejected→驳回`、`cancelled→已终止`）。
- **`blocked` 是派生条件而非核心态**：由巡检计算（`in_progress` 且 >48h 无更新 / 缺前置输入 / 等待他人），
  作为任务卡上的一个**标记位/预警**叠加显示，不进核心状态机——避免破坏编排流转合法性校验。
- **`archived` 是软生命周期标记**：新增 `archived_at`（或复用既有软删语义），不占执行态槽位。

> 这样做的收益：任务卡对上（用户看板）呈现 PRD 语义，对下（durable runtime）保持不变量。
> 这是本次升级里最需要评审确认的一个架构取舍。

### 5.3 「项目（Project）」是真正的新聚合
现有代码**没有任务分组的项目概念**。看板/时间线/项目概览/项目归档都依赖它。
→ 在 `task_management`（或新 `business/project_workspace` 叶子 Context）内新增 **Project 聚合**，
任务卡增加可空 `project_id` 外键。归档时项目关联内容自动进个人知识库（联动 6.4 知识沉淀）。

## 六、数据模型增量（context-owned，非横切）

> 原则：新表**归对应叶子 Context 所有**，Alembic 迁移续 `045` 之后（`046_*`…）。**禁 `workspace_` 横切前缀**。
> 命名随所属 Context 语义（示例名，评审后定稿）。

| Project（项目） | `task_management` / 新 `project_workspace` | 任务分组、项目概览、归档 | 任务卡加 `project_id` |
| InboxItem 读态（已读/处理/优先级分数/AI摘要） | `work_desktop` | 收件箱去重 + 状态持久化 | 现为纯读投影，需落持久态 |

## 七、分阶段开发规划（重构豆包 4 期）

> 豆包按「从零建」估 6+6+6+4 周。因大量底座已存在，工作从「建」转为「聚合/激活/前端外壳」，
> 阶段目标据此重排。周数为**相对工作量参考**，非承诺工期；每阶段独立验收再进下一阶段。

### 阶段 A — 任务抽象收口 + 工作台外壳 + 收件箱增强（最痛优先）
**目标**：跑通「任务管不过来」——统一任务卡 + 项目 + 看板 + 增强收件箱，5–10 人内测。
- 统一任务抽象层收口：5 类来源统一进任务卡；看板泳道派生投影；`blocked` 派生标记 + `archived`。
- **Project 聚合**新建 + 任务 `project_id`；项目概览/归档最小版。
- 看板前端外壳（`frontend/src/pages/workspace/`）：看板视图 + 列表视图（时间线/日历延后到 B）。
- 收件箱增强：优先级打分（4 因子加权，可人工调权重）、AI 一句话摘要、去重、已读/处理态持久化、批量处理（真人确认）。
- AI 任务中心「先出计划再执行」前端流（复用 `work_planning`+`workflow_runtime`，**不新建引擎**）。
- **红线**：批量审批=真人逐条/一次确认；任何对外发送停 `waiting_human`。

### 阶段 B — 个人知识中枢 + 智能日程与时间管理
**目标**：经验自动沉淀 + 时间智能规划，20–30 人内测。
- 个人知识：user_id 隔离命名空间；自动沉淀监听（AI 产出/文档/会议纪要/任务复盘事件 → 归档）；
  带来源的问答外壳（复用混合检索）；新建任务时 Top5 相关知识推荐。
- 智能日程（**整域新建**）：Schedule/Focus/TimeLog；智能排程**出建议**（用户确认后生效）；
  专注番茄钟 + 通知拦截（复用消息推送控制）；周度时间复盘报告。
- 会议闭环增强：会前推送 + 会后纪要待办自动进收件箱（复用 `meeting_management`/`convene`）。
- 时间线视图 + 日历视图补齐。

### 阶段 C — 协同沟通中枢 + 数据决策面板 + 灰度
**目标**：结构化协同 + 个性化数据洞察，全公司灰度。
- 协同：对话绑 task/project；消息转行动（转待办/AI 任务/**转提案走审批流**）；异步会商 + AI 观点汇总（结论真人确认）；跨部门协作面板（扩 `collaboration_requests`）。
- 数据面板：个性化指标卡（user_id）；AI 主动洞察定时推送（写收件箱）；一键深析复用 AI 任务；决策辅助卡（只辅助，真人决策）。
- 灰度：按部门/用户白名单开放；新手引导；运维监控面板（复用既有健康自检 `/api/v1/health/deps`）。

### 阶段 D — 主动巡检 + 五机制联动 + 全量上线
**目标**：AI 主动化收尾，越用越懂。
- **主动巡检引擎新建**（`report_scheduling` 定时驱动）：8 类风险场景每小时扫；分级 critical/warning/info；
  **产出只写收件箱/日报**；误报反馈调阈值。**红线：不自动催办对外、不自动改排期。**
- 每日仪式：8:00 晨间简报 / 12:00 检查点 / 18:00 复盘 / 周五回顾（顾问产出，同步上级真人点发）。
- 上下文包组装（复用 `ContextSnapshot`）；人机分工路由前端呈现（白名单锁 automatic 集合）。
- 个性化推荐加权迭代（先简单加权，YAGNI，后续再上模型）；性能打磨；用户手册 + 培训。

## 九、风险与主动推迟项（ponytail ceilings）

| 项 | 现状取舍 | 升级路径（何时补） |
|---|---|---|
